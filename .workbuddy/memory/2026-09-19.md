## 咨询：二维码出图该走离线工具还是网站内生成 + 2核4G 容量实测（穿插在部署等待期，未改任何代码）

- 用户问：「2核4G 服务器，用户生成二维码应该是下载离线工具生成好，还是网站内直接生成好，最多支撑同时生成多少」。
- **复核结论：现状正确，不用改。** 2026-09-15 已把「服务端渲染 PNG + zip」整体下线，改为「网站出码值 + 离线工具本机出图」（`app/pages/admin/generator/index.vue` L177 注释；`docs/handover/02-最新需求.md` L113）。本次用数据证实该决策。
- **★ 基准数据（本机 i5-12600KF / node22，用项目自带 `server/utils/code-generator.ts` + 已残留在 node_modules 的 `qrcode` 实测，不连库不写数据）**：
  - 生成 1 万条 32 位码（含 10 万~50 万已有码的重码检测）= **36~40 ms**；**每千码 ≈ 4 ms**（线性）。
  - `qrcode` 渲染 300×300 PNG = **5.99 ms/张**（单核串行）→ 1000 张 5.99 s → **1 万张 ≈ 60 s**，PNG 平均 3.1 KB/张（1 万张仅 30 MB，**内存不是矛盾**）。
  - 全库捞码建 Set：10 万行 **18 ms / 5.8 MB**、50 万行 **145 ms / 19 MB**（每字符串约 100 字节 V8 开销）。
  - `JSON.stringify(1 万码)` = 1 ms / 342 KB。
  - 本机库 `trace_code` 实际仅 **104 行**（规模效应测不出，故上列大数均为**构造数据实测**）。
- **服务器折算口径**：阿里云 2核4G（g6/c6 的 Xeon Platinum）单核 ≈ 本机 i5-12600KF 的 **1/2~1/3**，按 **2.5** 估。→ 1 万码出码 ≈ 100 ms、1 万张 PNG ≈ **150 s**。
- **⚠️ 真正的杀手不是"慢"而是"阻塞"**：Node 单进程、PNG 渲染是同步 CPU 循环 → 150 秒内**整个事件循环排队**，连公众端 `/trace` 扫码页一起卡死；叠 nginx 默认 `proxy_read_timeout 60s` ⇒ **必然 504 + 全站假死**。这是当初下线的根因，方案 B 绝不能加回来。
- **并发上限估算（现值 PM2 单实例 fork，单事件循环）**：库 10 万码时「生成 1000 码 / 请求」≈ **18 并发**、「1 万码 / 请求」≈ **6 并发**（即 ~6 万码/秒）；库涨到 50 万码 → 2、100 万码 → 1。真实业务是低频重任务（企业就几个码管理员），**2核4G 足够**。
- **🔴 顺带发现的真瓶颈（不是生成，是每次请求的固定开销）**：`server/api/admin/codes/generate.post.ts` **L43 `SELECT code FROM trace_code` 全表捞码**做重码检测 —— 每请求都要付一次随库量线性增长的 DB+内存成本，而生成本身只是 40 ms。码量到百万级时这条会成为唯一瓶颈。优化方向（**未实施，属登记项**）：按 `enterprise_id`/产品范围收窄、或改「靠唯一索引兜底 + 不再全量捞」。
- **方案 C（本次新提出，未实施）**：浏览器端出图（`qrcode` 浏览器版 + JSZip）——服务器成本归零、免装 90 MB 工具、不受 Windows 限制；代价是 DM 码/模组尺寸/静区/300 dpi 等**印刷级参数难对齐**，只适合小批量内部核对。**印刷主线仍应留离线工具。**
- **隐藏成本提醒**：离线工具 EXE **90.63 MB**，服务器带宽 1 Mbps 时下载需 ≈ 12 分钟且占满带宽（3 Mbps ≈ 4 分钟）。
- **容量真结论**：2核4G 的瓶颈**不在生成，在公众端扫码峰值**（`/trace` SSR + 多表查询，消费者集中扫同一批次才是压力点）。
