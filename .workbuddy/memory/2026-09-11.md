## UI 改版提示词手册（docs/UI改版提示词.md，提交 31285cd）

**背景**：用户反馈现有界面「不够简约舒适、AI 味有些浓」，诉求是**要提示词**（指导 AI 改 UI），不是直接改代码。

**诊断方法（可复用）**：
1. 读 `app/assets/css/main.css` 摸清令牌体系（`--ui-*` 映射 + `--b-*` 中后台设计语言，圆角 0.375rem，主色 hsl(142 32% 30%)）
2. 看 `screenshots/` 实况截图（home-mobile / trace-genuine-bound / login / admin-dashboard）
3. `grep gradient` + `grep #[0-9a-fA-F]{6}` 定位 AI 味写法的**具体文件行号**

**实测结论（重要，后续改版直接引用）**：
- AI 味头号出处：`app/pages/index.vue:41` 的 `bg-gradient-to-br from-primary to-emerald-600` + `shadow-lg shadow-primary/30`
- `app/components/TraceAlert.vue:73` 用 `cfg.gradient` 给正常/异常/作废三态各配一套渐变
- 色彩不统一：`main.css` 是沉稳深绿，页面里另有 emerald-600、`nearby-stores.vue` 自成一套色板（#f8f9f4/#2c5c3a/#e67e22）、`admin.vue` 硬编码 #283850
- **后台其实已有克制的 `.b-*` 设计语言，问题集中在公众端 H5 + 令牌未被统一遵守**
- `scan.vue:253` 的 linear-gradient 是扫描线动画，属功能性视觉，改版时保留

**方法论沉淀（写提示词的核心）**：
- 负面清单 > 正面形容词（「AI 味」是可枚举的写法集合）
- 给数值不给形容词（4px 而非「小圆角」）
- 必须先冻结设计令牌，再改页面
- 红线：只改样式与模板结构，禁碰接口契约（本项目契约变更频繁，最易误伤）
- 执行顺序：令牌 → 登录页（校准审美）→ 扫码结果 → 首页 → 后台 → 全局 grep 复查

**产出**：`docs/UI改版提示词.md`（5 段可直接复制提示词 + 六要素方法论 + 执行顺序 + 4 条可量化验收标准 + 模型审美回潮补救话术），PROJECT_LOG.md 已追加记录。

## 排查：广西田园「辛菌·吗啉胍」原药候选为何只有 2 家（只读分析，未改代码）

**问题来源**：用户在产品管理添加广西田园 PD20110775 辛菌·吗啉胍，选原药时下拉只有 2 家。

**实测数据（pesticide_reg 全库只读查询结论）**：
- 该产品登记行：PD20110775，content `5.9%`，ingredients 原文 `辛菌胺 0.9%、盐酸吗啉胍 5%`，`ingredient_main`=辛菌胺，`ingredient_all`=`["辛菌胺","盐酸吗啉胍"]`
- 候选池筛选条件（regdata.ts findOriginalPool）：`dosage IN ('原药','母药') AND ingredient_main IN (产品全部成分) AND 登记证在有效期内`
- **命中仅 2 条，且都是「母药」**：PD20101360 山东胜邦绿野化学有限公司 / PD20101189 陕西省西安嘉科农化有限公司
- **盐酸吗啉胍的原药/母药登记 = 0 条**（全库 grep 确认）；数据源里也没有「吗啉胍·辛菌」反序命名
- 结论：只有 2 家是**数据源客观事实**，不是系统 bug

**"两个成分可互换"的根因**：候选池按「成分集合」合并（`ingredient_main IN (...)`），未把候选绑定到具体成分；候选下拉只显示「登记证号 | 企业名（原药）」，不显示该候选属于哪个成分 → 界面上两个成分的原药看起来可任意互换。

**命名顺序规范（查到出处）**：混配制剂名称用「·」连接各有效成分通用名，**按中文通用名称拼音顺序排列**（《农药登记资料要求》农业部公告第2569号 附件11）。辛(xīn) < 盐(yán)，故规范写作「辛菌·吗啉胍」。数据源里 `ingredient_all` 数组顺序不统一（有的 ["辛菌胺","盐酸吗啉胍"]，有的 ["盐酸吗啉胍","辛菌胺醋酸盐"]），是源数据顺序，非命名语义。

**关键发现（待接线）**：`product_original` 表**已有 `ingredient` 列**（"对应有效成分名（提示溯源用，可空）"，db-init.mjs:98），但 **post/patch/get/trace 四处的 SQL 都没写没读**（只读写 reg_no/company）→ 该列恒为 NULL。扫码结果页 TraceResult.vue 现仅展示「原药登记证号 + 原药生产企业」，**不显示原料/成分名**。这就是用户要的「扫码显示原料及其对应厂家」的缺口。

**后续可选方案**：A) 扫码按 reg_no 联查 pesticide_reg 带出 `ingredient_main`/product_name 展示（改动小）；B) 录入时把每行原药绑定到具体成分写入已有 `ingredient` 列，扫码显示「成分 → 原料 → 厂家」（彻底解决可互换）。本次未实施，等用户定方案。

## 修复：合并 PR #1 后服务拉不起来（提交 3ab3bba + 02ac295）

**用户诉求**：`merge PR #1`（56261b0）后无法正常启动服务。

**排查结论：合并本身无罪**。PR #1 只改 3 个文件（`products/index.vue`、`products.post.ts`、`products/[id].patch.ts`），`package.json` 零改动、12 个依赖齐全。真实根因两条：

1. **照着 AGENTS.md 抄 npm 绝对路径**：文档写的 `E:\software\nodejs\install\node_modules\npm\bin\npm-cli.js` 属**另一台开发机**，本机无 E 盘 → MODULE_NOT_FOUND。本机 npm 10.9.7 本身完好，`which npm` 指向 `C:\Users\27475\.workbuddy\binaries\node\versions\22.22.2-2\`。**教训：AGENTS.md 里的绝对路径都可能是机器相关的，照抄前先验证存在性。**
2. **`.nuxt` / `node_modules/.cache` 是合并前旧世界的缓存**，与 vite 配置不匹配 → 依赖优化器卡死在 `[optimizer] scanning dependencies...`（等 100s+ 无进展），Nitro 虽已监听但上游 Vite 未就绪 → **全站路由 502**。清 `.nuxt`+`node_modules/.cache`(+`.vite`) 重启即恢复（Vite 秒建、Nitro 约 12s 就绪）。

**特征码（可复用）**：`502 + 端口已监听 + 日志停在 scanning dependencies` = 缓存失配，不是业务代码坏了。排查顺序应是「进程是否监听 → curl 真实路由看状态码 → 再怀疑代码」。

**顺带推翻两条长期过时记录**：
- 文档原写「**dev 模式在本机不可用**（Nitro + Node 24 + 中文路径），验证须退回生产构建」→ **实测 dev 模式完全可用**（Node 22.22.2 + 中文路径），该限制已由 af33393（xlsx 改内联依赖，Nitro 不再外置）修掉。
- 登录接口响应体 `user` 恒为 null 是**既有行为非 bug**：`login.post.ts` 先 `setAuthCookie` 再 `getCurrentUser(event)`，`setCookie` 只写响应头不回写请求 Cookie；前端 `useUser.ts:41` 登录后 `await refresh()` 重新拉 `/api/auth/me`，响应里的 `user` 仅作兜底回填。

**新增可复用资产**：
- `scripts/dev-start.mjs`：`--check` 只读体检（Node/npm、3100+3000 端口占用与 PID、依赖完整性、`.env` 键名**只报名不打印值**、**缓存新鲜度**=对比 `package.json`/`package-lock`/`nuxt.config`/`.env` 与 `git log -1 --format=%ct` 的最大值）；无参则体检后自动清过期缓存并启动；`--clean` 强制清；`--port` 换端口。**以后启动类问题第一步就跑它。**

## 补充：服务两小时后又掉了 + 修正脚本误报（提交 7bc443a）

**事实**：17:57 启动的 dev 进程在约 19:45 前被回收，端口无监听。**这不是项目 bug**——它是我以「会话内后台进程」方式派生的，生命周期不绑定会话，会话结束/回收时被一并清掉。已重新拉起（新任务 qzLLOC），`/`、`/login`、`/trace?code=1` 全 200。

**关键发现（推翻我上一条的部分说法）**：这次**没有清任何缓存**就启动成功——`Vite client built in 168ms`、`Nitro server built in 6010ms`（比上次清缓存后的 12288ms 还快）。所以「缓存过期导致卡死」这个归因**证据不足**：上次那次卡在 `scanning dependencies` 也可能是进程被回收所致，清缓存与恢复之间未必是因果。**关于缓存卡死的机制，目前只能说「现象观察到过、清缓存后恢复」，不能断言因果。**

**修正了我自己脚本的误报（真实缺陷）**：`dev-start.mjs` 的缓存新鲜度判定原本把 `git log -1 --format=%ct` 也算进参照时间 → 我提交上一条修复后立刻报「`node_modules/.cache` 早于最近一次 git 提交，属跨版本残留」。这是**误报**：提交代码（尤其只改文档）根本不影响 Vite 依赖预构建。修复：`CONFIG_FILES` 收窄为 `package.json`/`package-lock.json`/`nuxt.config.ts`，移除 git 提交时间参照，`.env` 也移出（只影响运行时配置）。验证：修正后报正常；`touch -d "2026-05-01" node_modules/.cache` 反向验证检测能力仍在。

**方法论沉淀**：**启发式判定的参照系必须与它要预测的失效原因同源**。要预测「依赖预构建缓存失效」，就只能用依赖清单与构建配置当参照；把 git 提交时间混进来，等于把「所有代码变更」当成「依赖变更」，必然误报。

**已向用户说明的复发条件分类**（见对话回复）：① 「启动起不来」里的缓存类——会复发，触发点是会改变依赖预构建结果的操作（pull/merge 切到不同 package.json、npm install、改 nuxt.config、锁文件漂移、上次进程被强杀留下半成品缓存）；② 「服务自己消失」——**100% 会复发**，因为当前是裸进程、无任何守护机制，且这条建议在项目历史里已提过三次仍未落地（bc33660 条目、交接文档、本轮）。
