# 2026-09-23 工作日志

## 08:4x 回答「非本平台码 + 产品内容有问题，界面怎么显示」

用户提问（应是从消费者视角问的）。读代码得结论，**未改任何文件**，但挖出一条值得记的产品设计缺口。

**结论：公众端根本没有"产品内容不符"的提示位 —— 因为这条链路拿不到产品内容。**

公众端 `/api/trace` 的输入只有 **32 位码 + IP**，**刻意不抓外部平台页面**（合规与性能边界），所以没有"另一侧可比"。它能显示的"问题"只有 4 种，全部来自**码本身 + 国家登记资料库**：

| # | 情形 | 判定依据 | 页面表现 | 组件 |
|---|---|---|---|---|
| ① | 编码结构非法 | 第1位≠1/2 或 第8位≠1/2/3（`isUnitCodeStructureValid`） | 结构卡脚注变**红**：「编码结构不符合32位单元识别代码规则，请高度警惕该产品。」 | TraceExternal / TraceNotFound |
| ② | 登记证已过期 | `expire_date < today` | 候选表格下方**红条**：「该登记证已于 X 到期…请勿购买使用。」 | TraceExternal |
| ③ | 后六位撞车（不唯一） | 同类别多候选 | **琥珀**提示「该后六位对应 N 个登记证，无法唯一确定，请按标签核对」+ 逐条列 | TraceExternal |
| ④ | 登记库查无此证 | 无候选 | 整页换掉 → 红色「未查询到该追溯码信息」+ 4 条可能原因（第 2 条随结构合规与否切文案） | TraceNotFound |

**「产品内容不符」只在后台「外部二维码核验」页看得见** —— 因为只有那一侧拿得到外部平台内容（粘贴正文 / 来源链接）。那里有 6 项逐项比对 + 三态（`match`/`mismatch`/`insufficient`），总状态判据 `mismatch ? 'mismatch' : …`，**产品名/持有人 mismatch 会落 `risk_alert(alert_type=5)`**。文案：结论「发现信息差异」/「已核验项目未发现差异」/「部分资料不足，无法完全判断」；条目状态「信息相符」/「发现差异」/「资料不足」/「不适用」。

**⚠️ 有意思的细节**：`external-reg` 页**也能**出现红色结构警告 —— 只要 `validLength && validCategory && registrationLast6` 成立（这样才能查登记库）而**第 8 位生产类型非法**，就会「已有候选 + 结构卡报红」同时出现。所以"命中登记库"和"结构合规"是两件独立的事。

**建议（待用户定，未执行）**：这是**架构边界不是 bug**（不抓外部页面的决策是对的：延迟/封禁/SSRF 面）。若产品上确实要公众端也提示"内容不符"，唯一低成本路径是让消费者**手动输入包装上的产品名**，服务端与登记资料做归一化比对 —— 但这会**新增一个公众可写的判定入口**，必须防刷，否则又是一条可被滥用的写路径。等用户决定是否记进 23 号清单（拟作 P2 产品待决项）。
