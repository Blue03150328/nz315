## ⚠️ 本机 dev 服务因大数量生成 OOM 崩掉（2026-09-21 17:2x）

**现象**：为跑上限改造而拉起的本机 dev（3100）连续运行 **5 小时 48 分**后崩溃：
```
FATAL ERROR: Reached heap limit Allocation failed - JavaScript heap out of memory
```
堆峰值 **4.1GB**，退出码 **134**（日志 `logs/_dev-limits.log`）。期间我做过：500000 / 200001 / 50000 / 10001 多次生成（含 19MB 响应）。

**为什么值得记**：这不是 dev 独占的问题，而是**同一套服务端代码的内存开销**在真实场景下的放大版：
一次大数量生成要同时持有 ①码数组 ②去重 Set（`generate.post.ts` 是 `SELECT code FROM trace_code` **全表**拉库内码）
③约 19MB 的 JSON 响应字符串 —— 瞬时数百 MB 级，且**多次重复跑之后内存回收不干净**（否则不会累积到 4GB）。

**对线上的直接影响（已写进 19 号执行单 §6.3 红字与 §6'）**：
线上 PM2 的 `max_memory_restart` = **800M**，若在线上跑满 50 万，**有被 PM2 重启、站点闪断的风险**
（17 号文档第 0 步已记「nz315 曾 2 小时内重启 5 次，头号嫌疑就是它」）。
⇒ 线上验收**只跑 5 万条**即可（本机实测 5 万条 0.15 秒），50 万那档在本机已验过（1712ms / 19.08MB）。
⇒ 若以后要常态化跑 20 万+，应把 `max_memory_restart` 调到 1200–1500M，**但该字段 `pm2 reload` 不重读，必须 `pm2 delete nz315` + 重新 start** —— 与「只许 reload」铁律冲突，需专门窗口。

**处理**：已重新拉起 dev 服务（`node scripts/dev-start.mjs`）。**结论：dev 里不要反复跑满 50 万。**
