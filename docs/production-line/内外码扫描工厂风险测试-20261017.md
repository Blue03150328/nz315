# 内外码扫描：工厂风险测试（2026-10-17）

## 结论与测试范围

本次检查本机工作区的统一生产扫码逻辑。当前分流、原文保存、本机持久化和收据计数机制已有自动化覆盖，但工厂现场仍存在异常无法恢复、扫错产品、重复计产量等风险。优先处理异常恢复链路，并明确“有效码数量”与“实际生产件数”的区别。

本轮只做检查和隔离测试，未修改业务源码、连接扫描仪、代登录或开工，未写入任何业务数据库，也未安装APK、推送或发布。现役网站与设备版本未逐文件核验，因此下述结论针对当前本机源码，不能直接当作线上故障回执。

验证结果：

- 网站现有测试：125通过、5既有跳过，0失败。命令：`node --test tests/*.test.mjs`。
- 安卓核心：原78项加8项风险特征测试，共86通过，0失败。执行真实WorkerStore与内存SQLite，未执行光学扫码或完整Android应用测试。
- 服务器定向：6项通过，执行真实`stockLineEvent`等函数，数据库调用使用可控SQL替身；不属于真实MySQL、HTTP集成或并发验收。

## 需要优先处理的缺陷

### 1. 统一扫码异常的后台核对缺少原文（高）

场景：内部码因工人授权等原因进入异常，管理员随后选择“已投产”核对。

`server/utils/line-production.ts:175`传给`stockLineEvent`的事件只有`code`和`kind`，没有`rawCode`。统一扫码分支会重新解析`event.rawCode`，所以即使32位码完整，依然返回“来源无法识别或标签网址、路径、码格式不正确”。定向测试复现该调用参数和拒绝结果；后台真实点击尚未执行。

工厂影响：已经投产的瓶子无法通过现有核对路径恢复入库，后台产量可能少计，异常记录长期挂起。外码的`code`本来为空，当前核对路径也不支持把外码异常重新认定为有效采集。

建议：完整携带原始事件资料核对，分别设计内码和外码的异常恢复规则；保留原收据与审计，重新验证产品、批次、权限和唯一性。

### 2. 内码被云端判异常后，原任务重扫仍被本机判重复（高）

场景：本机先把一枚内码判为有效，云端随后因授权或批次等原因返回异常。现场纠正问题后在同一任务重扫。

本机`ww_line_usage`仍保留首次有效扫描的占用，`WorkerStore.capture`会把新扫描标为`duplicate`。服务器若没有该码，又会因为`event.kind`不是`valid`拒绝新入库。本轮分别用真实SQLite和服务器决策函数复现，重建WorkerStore后仍然存在。

工厂影响：反复重扫和普通重启不能解决，可能形成“瓶子已下线、系统未入库”的死角。与上一项叠加时，普通重扫和后台核对两条恢复路径都受阻。

建议：依据服务器最终收据区分“已有效入库”和“曾经扫过”，建立受控重试／核对状态；不得通过清数据或删除原始事件处理。

## 已复现的生产风险与规则边界

| 优先级 | 现场情况 | 当前行为与工厂影响 | 建议 |
|---|---|---|---|
| 高 | 开工选产品甲，扫到产品乙的外部标签或宣传、物流链接 | 合法外站路径可被当有效外码，沿用产品甲的生产资料；目前没有核对外站实际产品身份 | 按供应商配置域名、标签路径和必要字段规则，首件核对产品；无法验证时明确标识 |
| 高 | 同一个包装上既有内部码，又有外部码，工人把两枚都扫了 | 内码1＋外码1＝有效采集2；当前没有两码与同一实物的配对关系 | 报表明确显示码数；若需要件数，应按实际包装流程配置主码或配对规则 |
| 高 | 同厂同证号同规格、不同商标，扫描尚未入库的新内码时选错SKU | 11位码头不包含商标；两个SKU可能码头相同，无法仅靠码头判断品牌，新码会依赖所选产品 | 生成／分配阶段保留可信的码与产品ID对应清单，现场加强首件与换品确认 |
| 中 | 同一外码的网址大小写、协议、首尾空格或附加渠道参数发生变化 | 分类仍为外码，但按完整原文哈希去重，多个写法可分别计有效；原文完全相同才重复 | 保留原文；根据各供应商协议提取稳定唯一标识，不能随意删除未知参数 |
| 中 | 扫码枪广播数据附带CR/LF回车换行 | 工人页直接接收原文，严格分类将其记为异常；旧页面有去终止符处理，工人页广播路径绕过该处理 | 实机核对广播输出与键盘模式；区分设备终止符与标签正文，避免把合法整批标签全判异常 |
| 中 | 两台设备离线扫描同一标签，班组直接相加本机有效数 | 两台先各计一次；收据到达后被判重复的设备会下调有效数 | 结算以服务器已确认结果为准，单列待上传和重复，不把离线本机数当最终产量 |
| 中 | 外厂标签是字母序号、非32位数字、无协议网址、首页或带片段的链接 | 当前统一生产规则记异常；32位纯数字优先按内码解释，其他平台的32位裸码可能因产品头不符被拒 | 上线前收集实际供应商标签样本逐种验收，明确支持格式 |

以上情况属于当前规则的边界或可复现能力，不等于现场已经发生错账。尤其“相同外码的不同网址写法”是否代表同一瓶，必须结合供应商编码协议确认。

## 已有保护与本轮验证限度

已有测试覆盖严格内外来源识别、本站坏链接不流入有效外码、同机重复留痕、内外分计、记录恢复、产品及原批资料锁定等。服务器源码有企业范围原文去重与序号／收据保护；本轮未重新做真实HTTP并发或MySQL事务集成验收，不把旧文档的测试记录计为本次实测。

扫码结果提示和提示音在本机保存后就会产生；云端仍可稍后改判重复或异常。班组培训应明确“已保存”与“服务器已确认有效”的区别。当前自动传码通常每10～15分钟一次，联网也可能暂有待上传记录。

建议现场验收按以下顺序执行，使用独立测试企业、专门产品和虚构标签：

1. 开工选错产品、同头不同商标、换批号和换日期，观察首件拦截与生产归属。
2. 一件双码、重复标签、多设备同扫，核对码数与实物件数。
3. 两台设备断网后交叉重复、重启恢复和恢复网络，最终核对服务器回执。
4. 扫码枪广播与键盘两种模式，检查回车、连续扫码、暂停后误触发。
5. 真实标签距离、反光、污损、打印浓淡和产线节拍；这些光学与硬件项目本次未测。
