## 1. 实测证据（2026-09-17 13:5x · 本机 node 直连，非浏览器缓存）

### 1.1 HTTP 侧：完全正常

| 请求 | 实测 | 判读 |
|---|---|---|
| `http://www.nz315.cn/` | **200** · 标题「农资315 - 农药追溯查询」· 24789 字节 | nz315 HTTP 入口正常 |
| `http://www.nz315.cn/MP_verify_OUOoNSqTrpZkfWli.txt` | **200** · 16 字节（=`OUOoNSqTrpZkfWli`） | 校验文件 HTTP 侧可取 |
| `http://www.nz315.cn/api/consumer/wechat/authorize?redirect=/profile` | **302** → `redirect_uri=http://www.nz315.cn/api/consumer/wechat/callback` | **回调地址就是 http**，且 nginx 有正确透传 `X-Forwarded-Proto` |

### 1.2 HTTPS 侧：一点没动，443 仍然是 cynx

| 请求 | 实测 | 判读 |
|---|---|---|
| 443 证书（SNI=`www.nz315.cn`） | `subject CN = www.cynx.cn` · `SAN=DNS:www.cynx.cn` · Let's Encrypt · 2026-11-17 到期 | **443 上没有 nz315 的证书** |
| `https://www.nz315.cn/` | **200** · 标题「广西超优农选电子商务有限公司 - 全品类农资供应商」 | 请求**被 cynx 接走** |
| `https://www.nz315.cn/MP_verify_OUOoNSqTrpZkfWli.txt` | **404**（cynx 的 Nuxt 404 页） | 微信若走 https 抓校验文件 → 必失败 |
| `http://www.nz315.cn/`（看是否 301 跳 https） | **200 直出**，`Location` 为空 | **80 端口未做 301 跳转**，14 号文档第一段尚未执行 |

### 1.3 凭据与微信侧：凭据有效，且微信错误**必带 errmsg**

用项目真实 `WECHAT_APP_ID` / `WECHAT_APP_SECRET`（本机 `.env`）向微信发起**故意用假 code**的请求：

```
HTTP 200 · Content-Type: application/json; encoding=utf-8
{"errcode":40029,"errmsg":"invalid code, rid: 6aab8193-...","openid":undefined}
```

- 返回 `40029 invalid code` 而非 `40125 invalid appsecret` → **这对 appid / secret 是匹配且有效的**；
- **微信的失败响应带了完整 `errmsg`** → 反过来说：**线上若显示「未返回 openid」（即 errmsg 为空），说明服务器拿到的根本不是微信的标准错误 JSON**。

### 1.4 由此可以确定的两条事实

1. **微信确实带着 `code` 回调到了我们的服务器。**
   理由：`缺少 code` 会走另一条分支报 400「微信授权失败：缺少 code」；线上报的是 502「未返回 openid」，
   而全仓库只有 `callback.get.ts` 一处会产生该文案 → **OAuth 第一步（授权页 → 回调）是通的**。
   → 也就是说：**当前 http 的 `redirect_uri` 被微信接受了**，"没配 https 就必然失败"在本例中不成立。
2. **卡点在第二步：`code` 换 `openid`，且微信没回可读错误。**

## 2. 代码层的根因与修复

### 2.1 为什么真实错误会消失

原实现（`server/api/consumer/wechat/callback.get.ts`）：

```ts
const tokenRes = await $fetch<any>('https://api.weixin.qq.com/sns/oauth2/access_token', { query: {...} })
if (!tokenRes?.openid) {
  throw createError({ statusCode: 502, statusMessage: '微信授权失败：' + (tokenRes?.errmsg || '未返回 openid') })
}
```

这里有两个盲区：

| 盲区 | 后果 |
|---|---|
| **A. ofetch 对非 JSON 的 Content-Type 会原样返回字符串** | 微信响应体一旦被标成 `text/plain`（本项目本机实测为 `application/json`，但历史上/不同接入层存在 `text/plain`），`tokenRes` 就是**字符串**，`tokenRes.openid` 与 `tokenRes.errmsg` **全是 undefined** → 必然落到「未返回 openid」 |
| **B. 只取 `errmsg`，不取 `errcode`** | 只要微信回的是**只有 `errcode` 没有 `errmsg`** 的响应（或字段名不同），同样会退化成「未返回 openid」 |

盲区 A 已用实验坐实：本地起一个 `Content-Type: text/plain` 的接口喂给项目自带的 ofetch ——
`typeof 返回 = "string"`、`openid = undefined`；换成 `application/json` 才拿到对象。

> 👉 这正是**「线上只告诉你失败、不告诉你为什么」**的成因，也是本次 502 无法直接定位的原因。

### 2.2 修复内容（commit `a372c7e`，master）

`server/api/consumer/wechat/callback.get.ts`：

- 新增 `callWechatApi()`：统一以 `responseType: 'text'` 取回，再手动 `JSON.parse`；
  解析失败 / 空响应 / 非对象内容都保留原始文本（`__raw`），不再让字段读取静默失败；
- 新增 `describeWechatFailure()`：错误文案 = `errmsg（errcode=…）`，缺失时回落到**原始响应片段**；
- 失败详情同时 `console.error` → 进入 **PM2 error log**，线上可查；
- `sns/userinfo` 同步改造（仍为「失败不阻断登录」）。

### 2.3 验证方式与结果

把该路由用 esbuild 转译后注入 mock 的 `$fetch`，**执行真实路由逻辑**，覆盖 6 个场景：

| 场景 | 结果 |
|---|---|
| ① 响应是字符串（text/plain）且含 `openid` | ✅ 登录成功、跳转 `/profile`（**旧代码在此必失败**） |
| ② 正常 JSON 对象含 `openid` | ✅ 登录成功 |
| ③ 字符串响应 `errcode=40163 code been used` | ✅ 报「code been used（errcode=40163）」← 旧代码只会说「未返回 openid」 |
| ④ 拿到 HTML（网关/网络异常） | ✅ 报错并附带原始 HTML 片段 |
| ⑤ 空响应 | ✅ 报「微信接口返回空响应」 |
| ⑥ 对象但字段缺失 | ✅ 报错并附带原始 JSON |

## 3. ⚠️ 必须核对的隐患：两个不同的 appid

| 位置 | 值 |
|---|---|
| 本机 `E:\二维码管理\.env` → `WECHAT_APP_ID` | `wx9bd4bc120dea3f98` |
| 本机 `.output/server/chunks/_/nitro.mjs` **内嵌**的 `wechatAppId` | `wx1a6093c716310340` |

两个 appid **都是真实存在的公众号**（用假 secret 请求均返回 `40029 invalid code` 而非 `40013 invalid appid`）。

含义与风险：

- Nitro 的 `runtimeConfig` 是**构建期内嵌**的（见 AGENTS.md 三条最容易踩的坑之一）→
  **线上实际用哪个 appid，取决于「服务器上那份 `.output` 是用哪份 `.env` 构建的」**，而不是服务器 `.env` 当前写了什么；
- 若**服务器产物内嵌的 appid ≠ 你在公众平台配置了「网页授权域名」的那个公众号**，
  就会出现：授权页用的是 A 公众号、域名却配在 B 公众号上 → 授权链路必然出问题；
- **因此：在部署新代码之前，必须先确认三者一致**（服务器产物内嵌值 / 服务器 `.env` / 公众平台待配公众号）。

```bash
grep -rho 'wechatAppId":"[^"]*"' /var/www/nz315/.output/server/ | sort -u
```

**判读**：输出里那个 `wx…` 就是**线上正在使用的公众号**。

### 4.2 服务器 `.env` 里写的是哪个 appid（AppID 属公开信息，可打印；Secret 不要打印）

```bash
grep '^WECHAT_APP_ID=' /var/www/nz315/.env ; grep -c '^WECHAT_APP_SECRET=' /var/www/nz315/.env
```

**判读**：第一行给出 `.env` 的 appid；第二行应输出 `1`（表示键存在）。
**若两者与 §4.1 不一致 → 就是问题的一部分**：产物是旧构建，`.env` 改了也没生效（未重建）。

### 4.3 服务器出网到微信是否正常

```bash
curl -s 'https://api.weixin.qq.com/sns/oauth2/access_token?appid=x&secret=x&code=x&grant_type=authorization_code'
```

**判读**：
- 返回 `{"errcode":40013,"errmsg":"invalid appid, rid: …"}` → **服务器出网正常**（微信能正常回 JSON）；
- 返回 HTML / 空 / 超时 → **出网链路被拦截**，这才是「errmsg 为空」的真正来源，需查服务器 DNS / 代理。

## 5. HTTPS 到底要不要配？

### 5.1 对这次 502：不需要（不是它的锅）

实测已证明：http 侧首页 200、校验文件 200、`authorize` 生成的回调正确、**微信也把 `code` 送回了服务器**。
也就是说本例中 **http 的 OAuth 链路是通的**，把 502 归因于「没配 https」是误判。

### 5.2 但 HTTPS 仍然必须配，理由按优先级排列

| 优先级 | 理由 |
|---|---|
| 🔴 P0 | **443 现在是 cynx 的** —— 任何人访问 `https://www.nz315.cn` 都会看到**别家公司的网站**，且证书是 cynx 的。这是明确的事故隐患（用户会以为进了钓鱼站） |
| 🟠 P1 | 微信官方与社区一致口径：网页授权 `redirect_uri` **应为 https**。现在能用属"灰色可用"，微信收紧校验时会突然失效 |
| 🟠 P1 | 微信**校验文件必须放域名根目录**；一旦微信改为走 https 抓取，当前 `https://…/MP_verify_*.txt` = **404**，域名配置会直接失效 |
| 🟡 P2 | 后续要接微信 JS-SDK（分享卡片、扫码等）时**强制要求 https** |
| 🟡 P2 | 微信内打开 http 页面会显示「非微信官方网页」提示条，影响体验与转化 |

### 5.3 执行路径

照 `docs/handover/14-微信网页授权域名配置流程.md` **第一段（补 HTTPS，4 步）** 走：
签证书（阿里云免费证书 · DNS 验证）→ 证书落位 → 改 `nz315.conf`（80 跳 301 + 443 反代 3100）→ `nginx -t && nginx -s reload`。

⚠️ 三条硬约束（来自 14 号文档，勿忘）：**绝不在 `nz315.conf` 写 `listen 443 ssl default_server`**（会抢 cynx 的默认 443）；
**不做裸域名 `nz315.cn` 的 443 块**（单域名证书会不匹配）；**只用 `reload`，绝不 `restart`**。

## 6. 部署注意（先别急着部署新代码）

1. **先做完 §4.1–4.3**，确认 appid 口径一致。**在 appid 未核对清楚前构建部署，可能把线上 appid 换成另一个公众号**，反而更难排查。
2. 部署方式沿用现有手册流程（打包 → 上传 → 解包 → **还原服务器上的 PM2 修正版配置** → `pm2 reload`），
   其中「还原 PM2 配置」这一步**不能省**（仓库版 `deploy/ecosystem.config.cjs` 是 3000 端口版，会盖掉服务器上的 3100 + interpreter 版）。
3. 因 `runtimeConfig` 构建期内嵌：**构建机 `.env` 的 `WECHAT_APP_ID` / `WECHAT_APP_SECRET` 必须是最终要上线的那一套**。
4. 修改后重试时，若看到「code been used」，说明该 code 已被消费过（同一个回调链接被重复打开），**重新从「我的」页发起一次登录即可**。
