>

## 2. 根因链路

```
外站应答：HTTP 200 · 17,424 B · 服务端渲染 · 字段齐全
      ↓
sourceText()：去脚本、块级标签转换行
      td 内嵌 div ⇒「品种名称：」与「亨达美田」被拆成两行、各剩一格
      ↓
parseSourceDocument()：含标签路径「只按 Tab 切」+「只认同行『标签：值』（冒号后必须有值）」
      两行各只剩一格 ⇒ 无「冒号后有值」也无相邻单元格 ⇒ pairs 为空
      ↓
source-snapshot.ts 三空判据触发抛错
      productName · registrationNo · originals 全部为空
      ↓
前端显示：「这个来源页面要靠浏览器才能显示内容」  ← 与事实相反
```

**验证方式（可直接复用）**：把抓到的 HTML 直接喂给项目自己的解析器 ——
`node --experimental-strip-types` 能直接 import 项目 `.ts`：

```js
import { pathToFileURL } from 'node:url';
const mod = await import(pathToFileURL('E:/二维码管理/server/utils/source-parser.ts').href);
const src = mod.parseSourceDocument(html, url, code);
// 修复前：只返回 sourceUrl / platform / code，productFields: []、originals: []
```

### 4.1 🔴 为什么「品种名称」单独成档、绝不能并进 `productName`

该页面写的「品种名称：**亨达美田**」是**商品名**，而这张登记证 `PD20241818` 在登记库里的
**农药名称是「丙硫菌唑·戊唑醇」**。一旦把「品种名称」并进 `productName`：

```
比对项「产品名称（不含百分比标注）」：亨达美田  vs  丙硫菌唑·戊唑醇  ⇒ mismatch
```

⇒ **正规药当场被报成「与登记资料不一致」**，正是 36 号 §11.3 边界 2 特意要防的那类误报。
故本轮采用**只展示、不参与强比对**（用户 2026-09-27 裁定，即「选项 A」）。

> 注：`server/utils/source-snapshot.ts` 的 `referenceProductFor()` 里那条「**不扩展到通用解析出来的、
> 有名称没证号的页面**」的边界，与本裁定同源，**本轮一字未动**。

### 4.2 为什么必须升 `SOURCE_PARSER_VERSION`

快照缓存键 = `sha256(sourceUrl + code + SOURCE_PARSER_VERSION)`。**不升版 ⇒ 10 分钟内会复用旧结果**，
修复对刚查过的码不生效。凡改解析口径必须同步升版（`.2` → `.3` 同理）。

## 6. 36 号 §4.1 判据修订（**重要**）

36 号 §4.1 给的判据是「**抓下来去标签后，标签后面还有没有值**」——用它判断"该不该做适配器"。
**本案例证明这条判据不够**：该页面用粗暴去标签**确实有值**（423 字符全在），
但走我们自己的 `sourceText()` 行结构后仍取不到 ⇒ 按 36 号判据会误判成"不需要处理"，而实际是我们自己的 bug。

> **修订后判据**：「**标签与值是否落在同一个 Tab 分隔的单元格内**」。
> 不在同一格（被块级标签拆行）⇒ **先修通用解析器，不要按平台铺开写适配器**。

另：`tests/source-snapshot.test.mjs` 里原有一条注释写着

```
// 边界（刻意保留，待裁定）：含标签的 HTML 不启用「分行」兜底 ⇒ 块级逐行渲染的页面仍取不到字段；
// 若要对 HTML 也启用，会同时改变公众端 /api/trace 外页快照的填充口径，需另行决定。
```

—— 这就是 2026-09-24 留下的**待裁定技术债**。2026-09-27 裁定为「启用」，且它担心的
「填充口径会变」已由 §5.1 的对拍**实测排除**（三个既有站逐字节未变）。该用例已同步更新。
