## 2. 逐条详述

### N1 【P1·线上已存在】产品建档不校验登记证号是否存在 —— PRD「建档时阻断」缺失

**PRD 依据**（§5.9 异常清单 第 3 条）：
> 「登记证号不存在 | 扫码解析出的登记证号在农业部数据库中查不到，**涉嫌伪造登记证** | 对接中国农药信息网校验 | **后台预警 + 产品建档时阻断**」

**实测（端到端，本机 dev + 本机开发库）**：

```
pesticide_reg 中 PD99999999 的条数 = 0（0 = 确实不存在）
使用账号 = lvfeng / enterprise_admin
POST http://127.0.0.1:3100/api/admin/products   body: { registrationNo: 'PD99999999', ... }
→ HTTP 200
→ 响应体 = { "ok": true, "id": 23 }
→ 库中已落盘该产品行数 = 1 ids=23
⇒ 判定：建档未被阻断（PRD 要求阻断）
清理: product_id=23 product_original 删 1 行 / product 删 1 行；清理后残留 = 0
```

**源码证据（三处，全在 master 版本里）**：
- `server/api/admin/products.post.ts:25` 只校验登记证号**非空**；`:38` 只查**本系统内是否重复** —— **从不查 `pesticide_reg`**。
- `server/api/admin/products/[id].patch.ts:24-25` 同样只有非空校验（编辑路径同样不阻断）。
- `app/pages/admin/products/index.vue:496` 的输入框是**自由文本**，占位符原文写着「选中产品自动带出，**可修改**」。
- 全仓库 **零** 处 `triggerAlert(alertType=3)` —— 连「后台预警」这一半也没有（详见 N3）。

**影响**：这是 PRD 为「伪造登记证」专门设的闸门。现状是**任意填写一个格式合法但库里不存在的登记证号即可建档 → 生成追溯码 → 消费者扫码看到「登记证号 PDxxx」而该证不存在**，且不产生任何预警。防伪平台的主防线在这里是开着的。

**建议修法**：建档/编辑接口对 `registration_no` 做**完整证号精确匹配** `pesticide_reg`（97,471 条），不存在即 `400` 阻断 + 落 `risk_alert(alert_type=3)`。
⚠️ **需要用户先定一个口径**：是否允许「新证/尚未收录」的显式豁免通道（否则真实新证会被堵死）。**注意**：23 号 D-1 的 8,914 条老证号（`PD91109-10` 形态）是**后六位**含非数字，按**完整证号**匹配不受影响。

### N2 【P1·线上已存在】公众端「信息有误，点此反馈」入口不可达 + 功能是 stub

**PRD 依据**（§5.9 异常清单 第 7 条）：
> 「扫码信息与标签不符 | … | 人工举报入口 + 定期抽查比对 | **扫码页「信息有误，点此反馈」入口** + 核实工单」

**源码证据（三段闭合，且 master 里就是这样）**：

| # | 位置 | 事实 |
|---|---|---|
| ① | `shared/types/trace.ts:11` | `TraceResultType` 里**声明了** `'mismatch' // 扫码信息与标签不符（8类异常-7）` |
| ② | `server/api/trace.get.ts` | 全部产出值只有 **8 个**：`not-found`(:43) · `external-reg`/`not-found` 三元(:69) · `voided`(:124) · `frozen`(:132) · `reg-expired`(:189) · `expired`(:200) · `repeat`(:216) · `genuine`(:226) —— **`mismatch` 一个都不产出** |
| ③ | `app/components/TraceAlert.vue:145` | 按钮 `v-if="outcome.resultType === 'mismatch'"` ⇒ **永不渲染**；`:64-66` `handleFeedback` 只弹 `toast`「**信息反馈功能建设中，敬请期待**」 |

**master 版本实测（证明线上同样如此）**：

```
master:shared/types/trace.ts         含 "mismatch"                = true
master:app/components/TraceAlert.vue 含 "resultType === 'mismatch'" = true
master:server/api/trace.get.ts       含 "'mismatch'"              = false
ycdb:server/api/trace.get.ts         含 "'mismatch'"              = false
```

**影响**：**双重失效**——入口的门开在一个**永远不会出现的值**上，而且门后**也没有功能**。消费者即使发现「信息与标签不符」，在公众端**没有任何反馈通道**，PRD 要求的「核实工单」也无从产生。类型 7 目前唯一能落预警的路径是**后台人工做「外部二维码核验」**（`external-verify.post.ts:25` 把 mismatch 项映射到 3/5/6/7），消费者侧完全缺席。

**建议修法**：二选一，**都要用户拍板**：
- ① **做**：入口条件改成对「消费者可感知的异常」开放（`repeat` / `reg-expired` / `expired` / `frozen` / `external-reg` 任选），后端新增反馈工单表 + 写接口（**公众可写 ⇒ 必须防刷**，这是它当初被搁置的原因）；
- ② **不做**：按本期豁免处理，但要**同时删掉 `'mismatch'` 这个空头类型**和这个死按钮，避免下一个人也被它骗一遍（并把它记进 PRD 台账的豁免栏）。

### N3 【P1·线上已存在】「每日定时巡检」机制整体不存在

**PRD 依据**（§5.9 业务规则 1）：
> 「第 1、7 类由**扫码行为实时触发**；第 3、4、5、6 类由**每日定时巡检**触发」

**源码证据**：
- 全仓库（排除 `node_modules`）**没有任何** `cron` / `node-cron` / `setInterval` / Nitro 定时任务；`server/` 下**唯一的 `setTimeout`** 在 `server/utils/ip-geo.ts:75`，作用是限速等待。
- `triggerAlert` **全项目只有 3 处调用点**：
  | 调用点 | 产出类型 |
  |---|---|
  | `server/api/trace.get.ts:184` | **4**（登记证已过期，扫码时触发） |
  | `server/api/trace.get.ts:211` | **1**（重复查询） |
  | `server/api/admin/external-verify.post.ts:27` | 由 mismatch 项映射 **3 / 5 / 6 / 7**（**人工**核验时才触发） |

**⇒ 推论（这是本条的要害）**：`ALERT_TYPES` 定义了 8 类，但**实际有触发路径的只有 1、3、4、5、6、7**（且 3/5/6/7 依赖人工操作），**类型 2 与 8 没有任何代码路径能产出**；而 **3、6 在自动链路上永远不触发** —— 因为「登记证号不存在」（N1 已证建档不拦）和「生产厂家不符」都只能由**每日巡检**发现，而巡检不存在。

**影响**：
1. 类型 4 的机制与 PRD 不一致：现在只在**有人扫码时**才预警 ⇒ **没人扫 = 永远发现不了过期产品**（巡检的意义就是「不依赖扫码」）；
2. 类型 3 / 6 实际上是死的；
3. 「风险预警中心」列表里的类型筛选（`app/pages/admin/alerts/index.vue:25` 有 8 项）中，**类型 2 与 8 永远是空的**（PRD 对这两类的处置不含「后台预警」，属可接受的空筛选项，但 UI 上没说明，容易被当成 bug 报）。

**建议修法**：加一个每日定时任务（Nitro 定时任务，或在宝塔加 `crontab` 调一个**带内部token保护**的接口），每日巡检：① `product.registration_no` 是否在 `pesticide_reg` 内（→ 类型 3）；② 产品名/持有人与登记资料是否一致（→ 类型 5/6）；③ 登记证是否过期（→ 类型 4）。

### N4 【P1·线上已存在】「登记证已过期 ⇒ 暂停绑定批次」未实现

**PRD 依据**（§5.9 异常清单 第 4 条）：
> 「登记证已过期 | … | 「登记证有效期至」< 当前日期 | **扫码页提示 + 暂停绑定批次**」

**源码证据**：`registration_expire` 这个字段在全仓库**只出现在 3 个地方**，且**没有一个在绑定链路上**：

| 位置 | 作用 |
|---|---|
| `server/api/trace.get.ts:182,186` | **只读判断**：扫码时比对今天，给消费者红字提示 |
| `server/api/admin/products.post.ts:66` | 建档时写入 |
| `server/api/admin/products/[id].patch.ts:46` | 编辑时写入 |

**所有绑定批次的接口都没有该字段的任何校验**（以下 4 个文件与 master **逐字节相同** ⇒ **线上同源**）：

```
server/api/admin/codes/batch-correct.post.ts:53          UPDATE trace_code SET batch_id = ... WHERE ... AND status = 1
server/api/admin/codes/[id]/correct.post.ts:56
server/api/admin/codes/upload-batches/[id]/correct.post.ts:114,120,143,149,186
server/api/admin/batches/[id].patch.ts:41
```

**影响**：登记证已过期的产品**可以正常绑定批次、正常出码、正常被扫到**；消费者侧只有一句红字，**生产侧零阻断**。PRD 的处置层级里「暂停绑定批次」是生产侧唯一的硬控制点，现在缺失。

**建议修法**：绑定接口在写入前联查 `product.registration_expire`，`< today` 即 `400` 并给出明确文案（「该产品登记证已于 X 到期，不可绑定生产批次」）。

### N5 【P1·线上已存在·公网可见】门户首页在展示「伪造统计数字」

**实测（本机 + 公网各一次）**：

```
本机：GET http://127.0.0.1:3100/api/stats   → {"totalQueries":128630,"abnormalClues":42}
      本机首页 SSR                          → http=200 bytes=24526，含 128630 = true

公网：GET https://www.nz315.cn/api/stats    → {"totalQueries":128630,"abnormalClues":42}   http=200
      GET https://www.nz315.cn/             → http=200 bytes=25151，含 128630 = true   ← 线上首页就在显示它
```

**源码证据**：`server/api/stats.get.ts` **全文只有 8 行**，是硬编码返回值，注释原文：

```ts
// 演示统计接口：支撑首页统计卡片；后端需求确认后替换为真实统计
export default defineEventHandler(() => {
  return { totalQueries: 128630, abnormalClues: 42 }
```

消费方：`app/pages/index.vue:8` SSR 拉取，`:99` 渲染 `stats?.totalQueries`、`:108` 渲染 `stats?.abnormalClues`。

**影响**：一个**防伪追溯平台**，在公众门户首页把**编造的累计查询量 128,630 次、异常线索 42 条**当真实业绩展示。这是「合规硬上线（11-01）」前最不该留的一类东西 —— 与刚修好的裸域名、正在补的备案相比，它更容易被监管方或媒体一眼看到；而且该接口**无鉴权、无缓存**，任何人都能取到并传播这两个假数字。

- ② **先撤下**：首页这两张卡片改成不依赖该接口的文案（宁可不显示，也不要显示假的）。

### N6 【P1·线上已存在】`/api/stores/nearby` 匿名可用 + 缓存无上限 + 与 `ip-geo` 共用 key

**实测**：
```
匿名（不带任何 cookie）GET http://127.0.0.1:3100/api/stores/nearby → http=200 {"located":false,"rows":[]}
```
（该接口无任何 `requireXxx` 守卫；`server/api/stores/nearby.get.ts` 不在 `master..ycdb` 改动清单里 ⇒ **线上同源**。）

**源码证据（四个问题叠在一起）**：

| # | 位置 | 事实 |
|---|---|---|
| ① | `server/api/stores/nearby.get.ts:16` | 缓存 `const cache = new Map<...>()` **没有任何条数上限**（对照：`ip-geo.ts:29` `CACHE_MAX = 5000`、`registry-lookup.ts:49` `CACHE_MAX = 500`） |
| ② | 同文件 `:18-19` | 缓存键 = 坐标取到 **0.01° 网格** ⇒ **换坐标即换键**，缓存完全可被绕过 |
| ③ | 同文件 `:50` | 只查 `Number.isFinite(lng/lat)`，**无范围校验** ⇒ `lng=999&lat=999` 也算合法 |
| ④ | 同文件 `:66-69` | 每次**缓存未命中**要打 **2 次高德**（关键词「农药」+「农资」各一页） |

**影响（两条，第 ② 条是链式的，比较隐蔽）**：

1. **内存无界增长** —— 攻击者用随机坐标连续请求即可无限扩大这个 Map。线上 PM2 的 `max_memory_restart` 只有 **800M**（项目记忆 / 23 号已记）⇒ 会触发周期性重启。
2. 🔴 **高德配额可被匿名刷爆，并连带绞杀 P1-1** —— `ip-geo.ts` 与 `nearby.get.ts` **复用同一个 `runtimeConfig.amapWebKey`**。而 23 号 P1-1 的两条实测约束写着：高德**限流/配额用尽时 HTTP 仍是 200**、只返 `status:'0'` ⇒ `ip-geo` 会**静默返 `null`** ⇒ **`scan_log.province/city` 又写不进去，「重复查询」重新退化成 P1-1 修复前的死分支**。
   ⇒ 也就是说：**P1-1 的修复依赖一个可被匿名刷爆的外部配额**，攻击者不需要碰扫码链路就能把它打回原形。

**建议修法**：① 缓存加 `CACHE_MAX`（对齐 `ip-geo` 的 5000）+ 简单淘汰；② `lng∈[-180,180] / lat∈[-90,90]` 范围校验；③ 按 IP 轻量限流（例如每分钟 N 次）；④ **给 `ip-geo` 换一把独立的高德 key**，让 POI 检索被打爆时不影响扫码省份写入（成本可接受的话，这是最干净的一条）。

### N7 【P2·仅 ycdb，未上线】`registry-lookup.ts` 注释与实现相反（隐患，当前不构成故障）

**源码**：`server/utils/registry-lookup.ts:47` 注释写「SQL 侧预取上限（**先按类别过滤再截断**）」，
但 `:81-84` 的实际 SQL 是 `WHERE RIGHT(registration_no,6) = ? LIMIT ?`（**没有类别过滤**），类别过滤在 `:88` 的 JS 里**之后**才做 ⇒ **是先截断再过滤**。`server/utils/external-verification.ts:280` 的同类查询更直接 —— **连 `LIMIT` 都没有**。

**实测（我原本怀疑这里会「静默丢候选」，数据把我否了）**：复刻该 SQL 跑真实库 97,471 条，
**单个后六位最多只有 6 行**（`3-2000` → 6 行；次高 `030010` / `040008` / `090026` / `060013` 各 5 行），
**远低于 `LIMIT 20`** ⇒ **当前数据量下永远不会触发截断，不构成故障**。

**⇒ 结论**：降级为「注释失真 + 未来隐患」。建议顺手把类别过滤**下推到 SQL**（例如 `AND (registration_no LIKE 'PD%' OR …)`），或至少把注释改对，免得下一个人按错注释推理。

## 3. 复核后**不成立**的怀疑（留档，避免下一轮重复劳动）

| 曾经怀疑 | 实测结果 | 结论 |
|---|---|---|
