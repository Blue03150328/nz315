## 1. 数据模型

### 1.1 新表 `farm_bill`（**本轮唯一 DDL**）

进 `scripts/db-init.mjs` 的 `DDL[]`（新库自动建）+ 无需 migrate 补列（全新表，无历史库包袱）。

```sql
CREATE TABLE IF NOT EXISTS farm_bill (
  id BIGINT AUTO_INCREMENT PRIMARY KEY,
  consumer_id BIGINT NOT NULL COMMENT '消费者ID（微信登录，consumer.id）',
  bill_date DATE NOT NULL COMMENT '记账日期（用药/购药日，默认当天可改；按月分组依据）',
  product_name VARCHAR(255) NOT NULL COMMENT '产品名称（快照；扫码带入或手填）',
  category VARCHAR(20) NULL COMMENT '类别：杀虫/杀菌/除草/杀螨/肥料/其他（白名单，可空）',
  crop VARCHAR(50) NULL COMMENT '作物（自由输入，可空）',
  quantity DECIMAL(12,3) NULL COMMENT '数量（可空）',
  unit VARCHAR(10) NULL COMMENT '数量单位：瓶/袋/包/桶/千克/升/亩（可空）',
  unit_price DECIMAL(12,2) NULL COMMENT '单价（可空）',
  total_amount DECIMAL(12,2) NOT NULL DEFAULT 0 COMMENT '总额＝数量×单价，也允许直接改总价',
  channel VARCHAR(50) NULL COMMENT '购买渠道（自由输入，可空）',
  remark VARCHAR(500) NULL COMMENT '备注',
  code VARCHAR(32) NULL COMMENT '来源追溯码（扫码记账写入；手动记账为空）',
  source TINYINT NOT NULL DEFAULT 2 COMMENT '1扫码记账 2手动记账',
  created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
  updated_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP ON UPDATE CURRENT_TIMESTAMP,
  KEY idx_consumer_date (consumer_id, bill_date),
  KEY idx_consumer_category (consumer_id, category)
) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COMMENT='农资记账（公众端用药/用肥花费）'
```

**设计要点**
- 归属唯一键是 `consumer_id`，**不做多用户共享**（记账是私人数据）。
- `code` 只做来源追溯，**不做外键**（手动记账没有码；且扫码的码可能不是本平台签发的）。
- `product_name` 是**快照**：产品改名/下架不影响历史账目。
- 单位 `DECIMAL(12,3)/(12,2)`：数量支持 0.001（如 0.5 千克），金额两位小数。

### 1.2 两个派生口径（**必须写死在实现里，否则统计会漂**）

| 指标 | 口径 |
| --- | --- |
| **用肥花费** | `category = '肥料'` 的 `total_amount` 之和 |
| **用药花费** | `category <> '肥料'` 的 `total_amount` 之和（含杀虫/杀菌/除草/杀螨/其他） |
| **总花费** | 全部 `total_amount` 之和（＝用药 + 用肥） |
| **覆盖作物** | `COUNT(DISTINCT crop)`，**排除空值**（作物允许为空，空值不算"一个作物"） |

> ⚠️ **实施时的两处修正**（相对本节初稿，已按下面这版落地）：
> 1. **`category` 落库恒为 6 类白名单之一**（空 → `其他`），库里**不存 NULL**。
>    初稿写"类别可空"会让饼图多出第 7 个分区、也让"用药 + 用肥 = 总"多一个口径分支；
>    改成"不选 → 其他"后统计永远干净（用户无感知，前端仍显示"未分类"）。
> 2. **用药 = 总 − 用肥**（而不是各自 SUM 一次）：保证恒等式在任何浮点情况下都成立。

### 1.3 类别归一化（`shared/utils/bill-category.ts`，新增）

扫码带入时把产品/登记库的原始类别压到 6 个白名单值：

| 原始值包含 | 归一化结果 |
| --- | --- |
| `杀虫` | 杀虫 |
| `杀菌` / `杀真菌` | 杀菌 |
| `除草` | 除草 |
| `杀螨` | 杀螨 |
| `肥` | 肥料 |
| 其余/空 | 其他（落库时空值允许保留） |

**放 `shared/` 的原因**：前后端都要用（前端预填、后端白名单校验），单一来源避免漂移。

### 2.2 校验与安全（逐条都是**已踩过坑的同族问题**，不许省）

1. **归属校验**：`PATCH`/`DELETE` 的 SQL **必须**是 `WHERE id = ? AND consumer_id = ?`。
   ⚠️ 只按 `id` 改是**水平越权**（本项目有 P0 提权前科，提交 `1db9535`）。
2. **写入限流**：复用 `server/utils/rate-limit.ts`，key = `bill:<consumerId>`，60 次/分钟。
   ⚠️ 限流位置放在**入参校验之后**（与 `feedback.post.ts` 的口径一致），否则正常用户改一次表单就被误伤。
3. **类别白名单**：非白名单值一律降级为 `其他`（或空），不做 400（用户手输不该被拒）。
4. **金额/数量**：`≥ 0`、上限 `999999999.99`；**`totalAmount` 优先采信前端** —— 用户明确要求"可以调整总金额"，
   故**允许总额 ≠ 数量×单价**（抹零、折扣、只记得总价都属正常）；仅在总额缺失时才按 `quantity × unitPrice` 兜底推算。
5. **日期**：`YYYY-MM-DD` 且落在 `2000-01-01 ~ 今天`（未来日期直接 400）。
6. **文本长度**：产品名 ≤255、作物/渠道 ≤50、备注 ≤500（服务端截断或 400，前端同步 `maxlength`）。
7. **年份参数**：`year` 非法时回落当前年（不 400，避免页面白屏）。

### 3.4 图表为什么自绘

项目**当前零图表依赖**（`package.json` 无 echarts/chart.js）。本需求只要 1 个柱状图 + 1 个环形图，
引入 ECharts（≈1MB，且本项目 `nitro.externals.inline` 手工维护白名单）**不划算**。
故用内联 SVG 自绘：柱状图 = `rect` 阵列 + `text` 刻度；环形图 = `circle` 的 `stroke-dasharray` 分段。
**零新依赖 / 零 nuxt.config 改动 / 不影响构建。**

### 11.3 相对方案的差异（7 处，均已落地）

1. **`category` 恒为 6 类之一**（空 → `其他`），库里不存 NULL —— 见 §1.2 修正。
2. **用药 = 总 − 用肥**，而非各自 SUM（保证恒等式）。
3. **`totalAmount` 优先采信前端**（方案初稿写的"不信任前端"是错的 —— 与"允许用户调整总金额"直接冲突）。
4. **新增 `localToday()` 兜底**：若 `CURDATE()` 取不到，`today=''` 会让日期校验把**所有**请求判成"未来日期" ⇒ 记账全量 400。
   这类故障极难排查，故统一在 `parseBillBody` 与 `analysis` 两处收口兜底。
5. **弹窗改「头部固定 / 表单滚动 / 按钮吸底」**：真浏览器实测发现保存按钮被推出屏幕（`inViewport:false`），
   而"扫码后顺手记一笔"正是核心场景 ⇒ 修完后断言 `inViewport:true`。
6. **柱状图纵轴改细档位**（1/1.2/1.5/2/2.5/3/4/5/6/8/10 × 10ⁿ）：原实现 1175 会被抬到 2000 刻度，柱子只占 59% 高度，视觉上像"没画满"。
7. **删掉 `isFertilizer()` 死导出**（构建后核查发现全项目零引用 —— 口径实际在 SQL 里）⇒ 在位留注释说明「刻意不提供 JS 判定函数」，防止日后有人靠它算出跟 SQL 不一致的第二套统计。
