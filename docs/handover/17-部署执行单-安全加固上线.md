### 期望输出（逐条对照，这三条是本次部署的"体检报告"）

① `dump` 应打印 4 行，**注意最后那句 `user.session_epoch 列：不存在（迁移前，按 0 记入基线）`**：

```

[verify] 表数=N · 企业=N · 账号=N · 追溯码=N
[verify] user.session_epoch 列：不存在（迁移前，按 0 记入基线）
[verify] 下一步：node scripts/db-init.mjs --migrate-only
```

② `migrate` 的**关键行**（其余行可能是别的历史列/索引，属正常）：

```
[db] 数据库就绪: nz315
[db] 14 张表创建完成
[db] 迁移：user 补充列 session_epoch（会话吊销）      ← 这一行是本次的成败点
[db] --migrate-only：已跳过演示数据（seed）与历史码归档（backfillUploadBatches）
[db] 初始化完成（仅迁移）
```

③ `compare` 结尾必须是一模一样这一行：

```

```

**判据怎么读（重要，别误判）**

- 行数比对分两类：**业务主数据严格相等**；`scan_log` / `operation_log` 是纯追加日志（线上真实消费者扫码、管理员登录都会写），它们**只增不减**且**不计入 FAIL**，会打印 `注意 ...（活跃表，允许正常增长）`——**这不是问题**。
- `session_epoch` 只留证不判定（登出/改密会让它变化）。
- **只有在业务表（`enterprise` / `product` / `batch` / `trace_code` / `upload_batch` / `product_spec` / `product_original` / `user` …）出现 `FAIL`，或 `MAX(id)` 自增位被推进时，才立刻停手贴我。**

🔴 **绝对不该出现**：`[db] ⚠️ 即将写入演示数据…` 或 `[db] 初始化完成（含演示数据）`。看到就是 `--migrate-only` 漏了，**立刻停手贴我**。

### 如果 `db-init` 报错（大概率只会是权限问题）

报错形如 `初始化失败: Access denied for user 'nz315'@'localhost' to database 'nz315'` —— 这是脚本开头那句 `CREATE DATABASE IF NOT EXISTS` 撞上了权限（应用账号通常只有 `nz315.*` 的权限）。**库和表都好好的，没有任何写入发生**，改走 SQL 备选即可（下面这条 ALTER 与 `db-init.mjs` 里写的**逐字符相同**）：

```bash
cd /var/www/nz315
while IFS='=' read -r k v; do v=${v%$'\r'}; case "$k" in DB_HOST|DB_PORT|DB_USER|DB_PASSWORD|DB_NAME) export "$k=$v";; esac; done < .env
M=/www/server/mysql80/bin/mysql
$M --no-defaults -h"$DB_HOST" -P"$DB_PORT" -u"$DB_USER" -p"$DB_PASSWORD" "$DB_NAME" -e "ALTER TABLE \`user\` ADD COLUMN session_epoch BIGINT NOT NULL DEFAULT 0 COMMENT '会话吊销时间戳（毫秒）：签发时间早于此值的 token 一律失效（登出/改密时刷新）' AFTER last_login_ip;"
$M --no-defaults -h"$DB_HOST" -P"$DB_PORT" -u"$DB_USER" -p"$DB_PASSWORD" "$DB_NAME" -e "SELECT id, username, role, session_epoch FROM \`user\` ORDER BY id;"
env PATH=/usr/local/node22/bin:/usr/bin:/bin node scripts/verify-db-migration.mjs compare
```

- 期望：SELECT 列出账号且 **`session_epoch` 全为 0**；最后 `compare` 仍是 **PASS**。
- 重复执行这条 ALTER 会报 `ERROR 1060 (42S21) Duplicate column name 'session_epoch'` —— **属正常**，说明列已经在位。
- **其它任何错误**：原样贴我，别继续。

### 5.0 先把离线工具包就位（★ 最易漏的一步，且**顺序不能反**）

**为什么必须在 `npm run build` 之前**：Nuxt/Nitro 把静态资源清单**在构建时写死进产物**（本机实测：`.output/server/chunks/_/nitro.mjs` 里逐条列着 `/tools/xxx.exe` 的路径、`etag`、`size`）。构建**之后**再往 `.output/public/` 里丢文件，清单里没有它 → **访问 404**，`pm2 reload` 也不管用。所以必须先放进源码目录 `public/tools/`，让构建自己带过去。

**先在宝塔「文件」里把 EXE 传上去**：

1. 宝塔面板 → **文件** → 地址栏输入 `/var/www/nz315/public/tools` 回车
2. 点 **上传** → 选 `E:\二维码管理\public\tools\nz315-qr-tool-v1.2.0.exe`（90.63 MB，耐心等）
   - 面板上传若卡住/超时 → 改用 SFTP 客户端（WinSCP / FileZilla），用登宝塔的同一套账号，传到同一路径
3. 传完回终端核对（**顺带删掉旧版**）：

```bash
cd /var/www/nz315/public/tools
ls -l
sha256sum nz315-qr-tool-v1.2.0.exe
rm -f nz315-qr-tool-v1.1.0.exe
echo "--- 删旧后 ---"; ls -l
```

**期望（逐字符对照）**

```
04373ae1dc21752636f1b68945edb2dca8cff19c8b005b2ace1070cbc0a72fe8  nz315-qr-tool-v1.2.0.exe
```

且 `ls -l` 显示 **`95035957`** 字节；删旧之后目录里**只剩 v1.2.0 这一个文件**。

🔴 **SHA256 对不上就别往下走** —— 90 MB 的二进制传坏不会报错，只会让印刷厂下到一个坏包。删掉重传。

> **旧版 v1.1.0 为什么必须删**：它是**另一套造码算法**（无 MD5 校验位）且内置的是 2025-06-01 的规格快照 ——
> 谁要是从收藏夹直链下到它，出的图会扫不开或与平台规格对不上。留着就是给客户埋雷。

### 5.1 装依赖 → 构建 → 重载

```bash
cd /var/www/nz315
free -m; swapon --show
env PATH=/usr/local/node22/bin:/usr/bin:/bin npm install --no-audit --no-fund
env PATH=/usr/local/node22/bin:/usr/bin:/bin npm run build
ls -l .output/public/tools/
pm2 reload nz315
```

**每步期望**

| 命令 | 期望输出 | 耗时 |
|---|---|---|
| `npm install` | `up to date`（本次依赖零变化，应很快） | 秒级 |
| `npm run build` | 末尾 **`✨ Build complete!`** | 1–2 分钟 |
| `ls -l .output/public/tools/` | **只有 `nz315-qr-tool-v1.2.0.exe`（95035957 字节）** —— 这就是「5.0 有没有生效」的判据 | 秒 |
| `pm2 reload` | `[PM2] Applying action reloadProcessId on app [nz315]` | 数秒 |

- ❌ **不要用 `npm ci`**（全量重装 780+ 包，10 分钟起步，3.5G 内存的机器容易 OOM）
- ❌ **不要改 `.env`**（改了必须重新 build 才生效）
- ❌ **不要 `pm2 restart` / `kill` / `delete`**，只要 `reload nz315`

## 5'. 卡住了怎么办（速查）

| 现象 | 原因 | 处理 |
|---|---|---|
| 解包后 `grep` 里 `PORT` 是 `3000` / 没有 `interpreter` | 包没传对或没解包成功（本轮起包内就该是 3100） | 用备份里那份盖回：第 3 步末尾的命令 |
| `verify ... dump` 报 `Unknown column 'session_epoch'` | 用的是**本轮修复前**的脚本（包传错/没解包） | 确认 `/var/www/nz315/scripts/verify-db-migration.mjs` 是 11,373 字节 |
| `db-init` 报 `Access denied ... database` | 应用账号无 `CREATE DATABASE` 权限 | 走第 4 步 SQL 备选（**不要**去动账号权限） |
| `db-init` 输出里出现「即将写入演示数据」 | **`--migrate-only` 漏了** | 立刻停手贴我，并跑 `verify ... compare` 看污染范围 |
| `compare` 在 `scan_log`/`operation_log` 上报「注意」 | 窗口期有真实扫码/登录 | **正常**，继续 |
| `compare` 在业务表报 `FAIL` | 真有问题 | 停手贴我（含完整 `compare` 输出） |
| `npm run build` 被 killed | 内存不够 | 确认 2G swap 在（`swapon --show`），停掉吃内存的进程重跑 |
| 站点 502 | 构建没跑或失败 | `pm2 logs nz315 --lines 50`；确认 `✨ Build complete!` 出现过 |
| 页面能开但样式/交互全乱 | `.nuxt` 缓存与进程不匹配 | `pm2 reload nz315`；仍不行则删 `.nuxt` 与 `node_modules/.cache` 后重建 |
| **cynx 打不开了** | ⚠️ 危险信号 | 立刻检查有没有执行过 `pm2 kill` / `pm2 delete all`；把 `/root/nz315-backup-*` 里的 `pm2-describe.txt` 贴我 |
| `pm2: command not found` | 登录 shell 的 PATH 异常 | 先 `which pm2`；**千万别**给它加 `env PATH=...` 前缀（Node 版本不一致会让 PM2 重建 daemon，cynx 跟着挂） |
