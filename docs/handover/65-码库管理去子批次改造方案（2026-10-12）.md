# 码库管理去子批次改造方案（2026-10-12）

一句话：把今天（63 号）刚建成的「总批次 → 已用子批次 / 剩余子批次」两级结构**压平成一级**——
**一次「完成本次上传」= 码库管理里的一条记录**，并删掉子批次、剩余批次、使用记录三块内容。

---

## 一、本轮定位

- **施工分支：`SMXT`**（工作区已切至 `1e2da58`，dev server 已停）。**做完不合并、不推送**，合并时点由用户决定。
- **性质：当天推翻当天的新设计。** 62 号（码库剩余数量与生产使用记录）、63 号（码库折叠父子批次）均为 2026-10-12 当天落地，本方案拆除其中的父子层级与使用记录。62 号作为历史记录保留，63 号中与采集器「完成本次上传」划界相关的实现**继续有效**。
- ⚠️ **63 号末尾警告继续有效**：不能直接推送含私人临时历史的 SMXT 分支，也不能复用旧上线包；后续发布需重新整理源码与含本次 DDL 的迁移流程。

## 二、需求口径（用户已确认）

| 项 | 结论 |
|---|---|
| 批次边界 | 扫描仪点「**完成本次上传**」处划界——**一个上传 = 一条记录**。边扫码边自动上传**不另起批次**；网络分段/重试/断网恢复沿用同一上传身份（与 63 号采集器实现一致） |
| 记录范围 | 只记录已「完成上传」的码；未采集的码、未完成的上传**不出现在码库** |
| 删除项 | 子批次层级、剩余子批次行、使用记录（整功能）、「新建批次并绑定」入口 |
| 剩余范围 | **只删码库的剩余行**；生产任务里「剩余码待审核 / 放行 / 转领」流程**保留不动** |
| 列表列 | 产品名称 / 规格 / 生产批号 / 生产日期 / 码数量 / 码状态 / 上传时间 / 上传来源 / 操作 |
| 时间列 | **只要上传时间**（一个时间点） |
| 上传来源 | **账号优先，无账号回退设备** |
| 操作 | 详细（码明细）、修正生产信息、冻结 / 作废 / 恢复正常、**作废整批** |
| 「作废整批」 | = 整批标记作废（**不物理删除**，保留 1049 可追溯性）；明细内仍可**单独作废某一条码** |
| 数量显示 | **`12,352张`**（千分位 + 「张」，去掉「万」「约」） |
| 历史数据 | 均为测试数据，**不做迁移**，旧结构可直接废弃 |
| 生产任务页 | **不动**，由用户同事另行处理 |

## 三、数据模型：现状 → 目标

### 现状（63 号建成）

```
upload_batch（总批次＝上传的码文件）
  └─ code_usage_batch（已用子批次；一个 production_collection_upload 一条）
  └─ 剩余（虚拟行，无实体表）
trace_code.upload_batch_id → 码的源码文件归属
trace_code.usage_batch_id  → 码的已用子批归属
```

### 目标

```
production_collection_upload / code_usage_batch（一次「完成本次上传」= 一条）
  └─ trace_code（该次上传成功写入的码）
```

- 列表主体 = **已用子批次本身提升为一级**；`upload_batch` 退为纯「码池」（仍保留 `trace_code.upload_batch_id` 用于码归属与校验，**不在码库 UI 呈现**）。
- 「剩余」概念在码库中**彻底消失**。

### 字段取数

| 列 | 来源 |
|---|---|
| 产品名称 | `code_usage_batch.task_id → production_task.product_id → product.name` |
| 规格 | `code_usage_batch.spec_name_snapshot`（NULL 时显示「原规格资料未记录」） |
| 生产批号 / 生产日期 | `production_task.production_snapshot` → 回退 `batch` |
| 码数量 | `COUNT(trace_code WHERE usage_batch_id = ?)` |
| 码状态 | 上述码的 `abnormal_flag` 汇总（正常 / 部分冻结 / 全部冻结 / 部分作废 / 全部作废） |
| 上传时间 | `production_collection_upload.completed_at`（北京时间） |
| 上传来源 | `upload.uploader_username/name` 优先；为空则回退 `production_device` 名称 |

## 十二、本轮踩坑（值得记一笔）

- **`git rm` 会让工作区文件「批量消失」**：本轮执行 `git rm` 后，`tests/` 与 `upload-batches/[id]/` 下**未被点名的文件也一起从磁盘消失**，`git status` 报一大片 ` D`。这与 `~/.workbuddy/MEMORY.md` 里记的「checkout/merge 后文件不落盘」是同一族故障。
  - **规避**：**不要用 `git rm`**。改用 `node fs.rmSync` 删文件，再让 `git add -A` 去记录删除。
  - **修复**：`git reset --hard HEAD` 可一次全量铺回（本轮实测有效，53 个文件全部恢复）。
  - `git status` 与 `git add` 本身安全，只有 `git rm` 触发。
