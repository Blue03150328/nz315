## 2. 架构简述

### 2.1 整体形态

**单进程全栈应用**：一个 Nitro 进程同时提供 SSR 页面与 `/api/*` 接口，无独立后端服务、无前后端分离部署。

```
浏览器（公众端 H5 / 管理后台）
   │  HTTPS
   ▼
[nginx 反代]（生产，本机暂无）
   ▼
Nitro SSR 进程 (node .output/server/index.mjs)
   ├── 页面渲染：app/pages/**（SSR 首屏 + 客户端水合）
   └── API：server/api/**（Nitro 文件式路由）
          ├── server/utils/db.ts        → mysql2 连接池 → MySQL 8 (nz315)
          ├── server/utils/auth.ts      → 后台会话（HMAC 签名 cookie）
          ├── server/utils/consumer-auth.ts → 消费者会话（独立命名空间）
          ├── server/utils/code-validator.ts / code-generator.ts → 码规则
          ├── server/utils/risk-alert.ts / notify.ts → 预警与站内信
          └── server/utils/regdata.ts   → 登记数据源匹配
```

### 2.3 请求链路要点

| 场景 | 链路 |
|---|---|
| 扫码查询 | `GET /trace?code=`（SSR 直出）→ 服务端读 `trace_code` → 写 `scan_log` → 异常判定（作废/冻结优先）→ 联查 product/product_original/batch → 渲染；命中条件时 `triggerAlert()` 写 `risk_alert` + 站内信 |
| 后台页面 | 路由守卫 `backend-guard`（客户端）→ 页面 `useFetch` 调 `/api/admin/*` → 服务端 `requireBackendUser`（同源校验 + 会话校验 + 企业启停/续费校验）→ SQL |
| 码上传 | `parse`（预校验）→ `import`（事务：查重 → 自动建批/归并 → 分块插码 5000/批 → 建 upload_batch） |
| 页面缓存 | 11 个业务页 `definePageMeta({ keepalive: true })` + `experimental.normalizePageNames`（组件 name 对齐路由名，否则后台页全叫 index 无法区分） |

### 2.4 认证与安全（`server/utils/auth.ts`）

| 机制 | 实现 |
|---|---|
| 会话 token | `base64url(userId.exp).HMAC-SHA256`，`timingSafeEqual` 恒定时比较，**有效期 7 天** |
| Cookie | `nz315_user`（后台）/ `nz315_consumer`（消费者），httpOnly + sameSite=lax + HTTPS 下 secure 自适应 |
| 两类身份隔离 | 共用签名密钥，靠 payload 命名空间前缀 `consumer:` 区分，**互换 token 必被拒** |
| CSRF | `assertSameOrigin`：非 GET 请求若带 Origin 且与 Host 不符则 403；**无 Origin 的请求放行**（保证 curl/API 客户端可用） |
| 暴力破解 | 登录失败限速：同账号+IP **5 次/分钟，超限锁定 15 分钟**（429） |
| 权限守卫 | `requireBackendUser`（登录+企业有效）· `requireWritableUser`（拒 viewer）· `requirePlatformAdmin`（总部专属） |
| 生产硬约束 | `SESSION_SECRET` 未配置或等于默认值时**启动失败/登录 500**（防会话伪造） |
| 审计 | `logOperation()` 从 `event.context.authUser` 取操作人（该上下文由 `getCurrentUser` 挂载，**勿绕过**） |

### 2.5 构建与运行

- 构建：`npm run build` → `.output/`（Nitro 单文件服务 + chunks）。
- **runtimeConfig 在构建时从 `.env` 读取并内嵌**——构建前必须确认 `.env`；运行期覆盖须用 `NUXT_<键名>` 环境变量（如 `NUXT_SESSION_SECRET`）。
- 启动：`node .output/server/index.mjs`（默认 3000，可用 `-p`/PORT 指定；本机固定 3100）。
- **dev 模式已恢复可用（2026-09-11 实测推翻旧结论）**：旧问题（Nitro 2.13.4 + Node 24 + 中文路径 → CJS external 生成 `file://E:/` 裸盘符 → ESM loader 500）已由提交 `af33393`（xlsx 改内联依赖，不再外置）修掉。启动方式：`node scripts/dev-start.mjs`（默认清缓存后启动，`--check` 仅体检）或 `start-dev.cmd`；常驻托管由 Windows 计划任务 `NZ315 Dev Server` + `scripts/dev-service.mjs`（进程内守护循环）承担（详见 §8）。

### 4.2 分支规范

- **现状**：只有 `master`，直接在 master 上开发（单人 + AI 协作模式）。
- **建议规范**（多人协作后启用，与现有历史兼容）：
  - `master`：随时可构建、可部署的稳定分支；
  - `feature/<模块>-<简述>`：新功能（如 `feature/renew-expire`）；
  - `fix/<模块>-<简述>`：缺陷修复（如 `fix/correct-batch-dup-500`）；
  - `docs/<简述>`：纯文档；
  - 合并方式：小步合并回 `master`，**一次提交只做一件事**（历史提交严格遵循此约定）。

### 4.3 提交规范（**强制契约**，见 AGENTS.md 用户全局偏好）

1. **一轮修改 = 一次提交**：禁止积压，禁止把多个主题混进同一提交。
2. **提交信息用中文 + 约定式前缀**：
   - `feat:` 新功能 · `fix:` 修复 · `docs:` 文档 · `refactor:` 重构 · `chore:` 杂项
   - 建议格式：`fix(影响模块): 一句话现象与原因`，正文说明改动内容与原因。
   - 真实示例：`fix(码库): 修正弹窗批号已存在时必 500——exist 解构误用导致永远走建批分支`（`bc33660`）、`feat(系统设置): 用户权限列表改为按厂家分组展示…`（`5cdcf0c`）。
3. **隐私红线**：`.env`、数据库凭据、密码、会话密钥、`backup/*.sql` **一律不提交**；提交前自查 `git status`（`.gitignore` 已排除，但新增文件需人工确认）。
4. **记忆备份**：重要变更除提交外，还须在 `PROJECT_LOG.md` 顶部追加变更记录，并同步更新 `AGENTS.md`「项目进度」段（让接手者从 `git log` 与文档两处都能看到演进）。

## 7. 架构约定与红线

1. **语言与文案**：UI 文案、错误提示、注释一律**简体中文**；标识符英文；JS/TS 严格模式（ESM/TS 天然满足，普通 `.mjs` 顶部写 `'use strict';`）。
2. **Nuxt 4 目录规范**：前端源码在 `app/`，`~/` 指向 `app/`；`server/`、`public/`、`shared/` 在根。
3. **两套视觉基调不可互串**：公众端农业绿友好风（渐变、rounded-xl、480px 移动壳）；后台克制 B 端风（`b-*` 类、4px 圆角、无阴影、中性按钮）。**后台新页面必须复用 `b-*` 类**（`b-table` 已内置单元格内边距，勿再写 `px-4 py-3`）。
4. **多租户隔离**：所有企业数据接口必须带 `enterprise_id` 过滤；拼接条件用 `' AND …'`（**绝不能 `' WHERE …'`**，会拼出双重 WHERE）；改完必须用**厂家账号**冒烟一次（总部账号不复现厂家 500）。
5. **接口契约变更**：改响应字段前先 grep 前端消费点（历史事故：`parse` 只返回前 20 条 preview，页面依赖全量 results → 导入恒空）。
6. **不得降级为假数据**：未配置凭据时明确报错（如微信 401/503）或功能性降级，**禁止返回伪造结果**（历史上清理过一个返回伪造登记证核验结果的演示接口）。
7. **外键**：数据库**无物理外键**，引用一致性靠代码；删除前必须自建引用检查。
8. **临时验证脚本约定**：`scripts/_tmp-*.mjs`（gitignore 排除），命名可复用；正式脚本才纳入版本管理。

## 9. Nuxt UI v4 迁移坑（改前端必看）
