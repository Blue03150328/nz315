## B. P1 —— 功能与安全缺陷（**代码问题，本轮实测确认**）

### P1-1 ✅ **已修复（2026-09-22，提交 `66b0f6b`）** —— `scan_log.province` / `city` 只有读、没有写 ⇒ 「重复查询」在真实链路上是死分支

> **状态**：`66b0f6b` on `ycdb`。改 2 文件 / +185 −4。**零 DDL**（`scan_log` 的 `province`/`city` 两列与索引本已存在）/
> **零新依赖**（复用 `runtimeConfig.amapWebKey`）/ **零 nginx 变更**。**尚未部署**到线上。

| 项 | 内容 |
|---|---|
| **现象** | PRD「8 类异常-1 重复查询」（判据 `queryCount >= 3 && COUNT(DISTINCT province) >= 2`）在**真实扫码链路上永远触发不了**；连带 `risk_alert(alert_type=1)` 也不会被真实扫码触发 |
| **证据** | **源码**：`server/api/trace.get.ts` 原第 94-96 行的 INSERT 列是 `(enterprise_id, code, product_id, scan_time, scan_device, scan_subject, ip_location, consumer_id)` —— **没有 `province` / `city`**；前端 `useQrScanner` 不上送位置、服务端不解析 IP。<br>**实测**：库中 `scan_log` **204 行**里 `province` 非空的**只有 3 行，且全是测试脚本预置**；刚插入的真实扫码行为 `{"province":null,"city":null,"ip_location":"127.0.0.1"}` |
| **影响** | 一个 PRD 明确要求的功能在线上是**死代码**；修复前只能靠 `seed-abnormal-demo.mjs` 预置跨省记录来演示该分支 |
| **修法（已落实）** | 新增 **`server/utils/ip-geo.ts`**：客户端 IP → 省市，数据源高德 `restapi.amap.com/v3/ip`。自带 **24h 成功缓存 / 10min 负缓存 + 全局限速（≈3 QPS）+ 单飞去重 + 内网保留地址直接跳过 + 失败静默返 `null`**。<br>`server/api/trace.get.ts` 的 INSERT 补上 `province, city` 两列；取 **「缓存命中即当场写、首见新 IP 交后台异步补齐（fire-and-forget）」** —— 公众端是唯一被陌生人高频打的路径，外部调用**不得阻塞扫码主链路**。<br>两条本机实测约束写进了文件头：① **限流/配额用尽时 HTTP 仍是 200**，必须显式判 `status === '1'`；② **未命中返回的是空数组而非空字符串**。 |
| **顺带修复的安全隐患** | 原 IP 取自 `x-forwarded-for` 的**第一个值** —— 而 nginx 的 `$proxy_add_x_forwarded_for` 会把**客户端自带**的该头拼在真实 IP 前面，取首值等于采信客户端自报归属地 ⇒ **「重复查询」的省份可被任意伪造**。已改走 `clientIpOf(event)`（优先 `x-real-ip`）。<br>**实测**：伪造 `x-forwarded-for: 1.2.3.4` + 真实 `x-real-ip: 221.216.1.1` ⇒ 落库 `ip_location = 221.216.1.1`（伪造值未被采信）✅ |
| **验收** | 临时脚本 **14 项断言全通过**。核心一项：**不给任何预置数据**，走真实 `/api/trace` 链路即可得到 `resultType = 'repeat'`、`reasons = ["该追溯码已被查询 22 次，超过 3 次阈值","查询地域跨 2 个省份（北京市、上海市）"]`，并生成 `risk_alert(alert_type=1)` ✅ —— 这正是本条的验收标准（不是"列写进去了"，而是"分支真的能触发"） |
| **原始优先级建议** | ~~11-01 合规上线前补齐~~ → **已完成；随 `ycdb` 一起上线即可** |

> ⚠️ **残留边界（不是缺陷）**：本机开发环境里扫码请求的 `x-real-ip` 往往是 `127.0.0.1`（内网 ⇒ 查不出省市），
> 这是**环境使然**；线上经 nginx 反代后 `X-Real-IP` 才是真实公网 IP（14 号手册 §2.3 已确认 `nz315.conf` 带
> `proxy_set_header X-Real-IP $remote_addr`）。**线上验证这条功能必须用公网 IP 打**，本机只能靠伪造头模拟。

### P1-2 登录响应 `user` 恒为 `null`

| 项 | 内容 |
|---|---|
| **现象** | `POST /api/auth/login` 返回 `{"ok":true,"user":null}` |
| **证据** | **实测**：原始响应体即 `{"ok":true,"user":null}`。<br>**源码**：`login.post.ts` 第 82 行 `setAuthCookie(event, u.id)` 写的是**响应** cookie，第 88 行 `getCurrentUser(event)` 读的是**请求** header ⇒ 必然取不到 → 返回 `null` |
| **影响** | 前端 `useUser.loginWithPassword` 靠紧随其后的 `await refresh()`（打 `/api/auth/me`）补回用户态，**正常路径无感**；但第 46-52 行的兜底「refresh 失败时回填登录响应」**永远填 null** ⇒ 该兜底形同虚设，refresh 一失败就会被弹回登录页 |
| **修法** | ① 后端直接在 `setAuthCookie` 后用 `u` 构造返回体（别走 `getCurrentUser`）；② 或前端删掉那段无用兜底 |
| **实测影响面** | 小（前端已绕过），但属"埋着没炸" |

### P1-3 🔴 SSRF 防护实际失效（点分内网 IPv4 全放行）

| 项 | 内容 |
|---|---|
| **现象** | 外部核验允许把任意来源网址交给服务端抓取；**`127.0.0.1` / `10.x` / `192.168.x` / `172.16-31.x` / `169.254.x` 全部放行** |
| **证据** | **源码**：`server/utils/external-verification.ts:9` 的 `PRIVATE_HOST = /^(localhost\|.*\.localhost\|.*\.local\|0\.0\.0\.0\|127\.\|10\.\|192\.168\.\|169\.254\.\|172\.(1[6-9]\|2\d\|3[01])\.)$/i` —— **末尾 `$` 要求整串匹配**，于是 `10.0.0.5` 这类点分 IP 全不匹配。<br>**实测**：`sourceUrl=http://127.0.0.1:3100/login` → **HTTP 200（成功抓取）**；对照 `http://localhost:3100/login` → **400 被拦** |
| **影响** | 内网探测 / 云元数据（`169.254.169.254`）可被当作跳板；当前仅本机有该功能（未上线），**上线即风险面** |
| **修法** | 去掉末尾 `$`，改为「前缀 + 点分」判断（或干脆做 IP 规范化后再判私网段）；DNS 解析后的地址同样要判（现有第 38 行已做，同样受该正则拖累） |

### P1-4 `assertSameOrigin` 可被 `X-Forwarded-Host` 绕过

| 项 | 内容 |
|---|---|
| **现象** | `Origin: https://evil.com` 配合请求头 `X-Forwarded-Host: evil.com` ⇒ 跨站校验通过 |
| **证据** | **实测**：该组合登录 **HTTP 200**；对照 `Origin: https://evil.com`（Host 为真实地址）→ **403**。<br>**源码**：`server/utils/auth.ts:180` —— `const host = x-forwarded-host \|\| host`，**优先信 `x-forwarded-host`** |
| **影响** | Origin 校验（防登录 CSRF）可被绕过。**但**：前缀比较的旧写法（`startsWith`）已修好，本次实测 `https://www.nz315.cn.evil.com` → 403 ✅ |
| **修法** | nz315 的 nginx server 块加 `proxy_set_header X-Forwarded-Host $host;` —— **改 nginx 即可，`nginx -s reload`，不需重建** |
| **⚠️ 别顺手"修"错** | **无 Origin 的请求必须继续放行**（API 客户端依赖），这不是漏洞 |

### P1-5 🔴 外部核验「产品名比对」对真实平台**误报并落风险预警**

| 项 | 内容 |
|---|---|
| **现象** | 真实第三方平台把「剂型 + 序号」写进产品名（如 `15%精草铵膦可溶液剂-2` vs 登记库 `精草铵膦`）⇒ 判为 `mismatch` ⇒ **写入 `risk_alert`** |
| **证据** | **实测**：构造产品名不匹配 → `overallStatus=mismatch` 且 `risk_alert` 计数 **+1**（`alert_type=5`，`external_verification_id` 已关联）。**源码**：`external-verification.ts` 的 `normalizeProductName` **只剥 `\d+%`**，剥不掉剂型与序号 |
| **影响** | 用一个真实农药的码去核验，**大概率得到假警报**并污染 `risk_alert` 表 ⇒ 预警中心可信度下降 |
| **修法** | 归一化再增强（剥剂型词表 / 序号 / 括号后缀），或把产品名不一致降级为 `insufficient` + 提示人工复核，**不落预警** |
| **⚠️ 改前必读** | mismatch 是会**落 `risk_alert`** 的，改判定口径等于改预警数据源 |
