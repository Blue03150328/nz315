# 下载、出图与手机包装实扫执行方案（2026-10-06）

## 目标与范围

按“电脑下载 → 离线出图 → 绑定核对 → 手机查询 → 包装样张 → 单厂家试用”执行，确认厂家能交付可用的码，客户能查到正确信息。

本单是四项实际操作的执行计划，不代表已经通过，不启动部署或造数。最新本机业务证据看48号，服务器版本、备份、切换与回退仍按49号。人工操作在物料和环境齐备时预算半天，问题修复与复测另计。

## 负责人及准备

| 负责人 | 工作 |
|---|---|
| 开发/验收支持（Codex） | 固定验收版本，准备隔离样本及预期结果，核对文件/图片码值，定位问题，汇总记录和清理核验 |
| 项目负责人（用户） | 安排厂家操作人员、手机与印刷样张，确认环境，最终决定业务开放 |
| 厂家码管理员 | 正常浏览器登录、选择产品、生成留档、下载、绑定及核对 |
| 印刷/车间人员 | 操作EXE或实际赋码系统，按正式尺寸与材质制作样张 |
| 厂家质检人员 | 手机扫码，逐项对照产品和生产信息，填写结果 |

一名厂家人员可以兼任多个角色。准备Windows电脑及常用Chrome/Edge、官方v1.2.0工具、安卓手机和iPhone各一台（有条件时）、微信、实际打印设备、标签材料及包装。缺少某类设备须在验收范围中明确记录，不能把未测设备列为通过。

建立验收文件夹：原始码文件、QR图片、DataMatrix图片、屏幕截图、印刷参数、手机结果记录分别保存。记录操作日期、网页/EXE版本、浏览器及手机型号、测试地址；实际开始时再核对部署指纹，不能沿用旧指纹认定版本。

## 第0步：确认环境与样本

1. 优先使用手机可访问的HTTPS验收环境，运行候选代码、连接隔离测试库。电脑导出的查询网址须指向同一验收环境，手机查询的码也必须存在于该环境。
2. 手机中的localhost指手机自身，不能用电脑localhost地址作为手机验收入口；也不能将本机测试码发往正式域名并期望查到本机数据。
3. 如没有HTTPS验收环境，先完成电脑下载、EXE及纸张解码核对；在49号最终执行单获批准后，在正式域名受控部署的停写窗口完成手机查询验收，再决定是否开放厂家业务。该路径下，部署前手机完整链路明确记为未验。
4. 主流程准备独立测试产品的12条新码，并记入验收清单；另准备未绑定、产品过期、登记证过期、冻结、作废、到期当天等专用样本。范围隔离测试再准备同生产批次的另一份码文件。各样本记录产品、规格、码值、批号、日期、有效期和预期提示。
5. 造数仅由开发/验收支持在确认环境后按独立清单执行，开始前记录业务基线。正式库不运行本机集成验收脚本；正式域名验证如确需样本，使用受控的独立验收数据及明确清理清单。

通过条件：版本、环境、样本归属和预期结果明确。环境混用先纠正，暂停手机查询验收。

## 第1步：普通浏览器实际下载（厂家码管理员）

1. 用正常Chrome或Edge登录验收环境，进入“追溯码生成”，选择指定产品和规格，生成12条。
2. 点击“入库留档”，确认新增12条且仍为未绑定；保存码库记录，防止页面关闭后丢失码资产。
3. 分别点击“导出TXT”“导出urls.txt”“导出CSV”；在电脑下载目录打开实际文件。确认不是零字节、错误页面或仅有成功提示。
4. TXT应有12个完整32位码；urls应有12个完整查询地址；CSV应有1行表头和12行数据。开发逐条核对三个文件的码值、唯一数量、产品/规格和网址。
5. CSV核对时用文本编辑器，或在Excel“从文本/CSV”导入时把码值列设为文本。不要用Excel按数字处理后保存的文件作为原始赋码文件；32位码超过Excel15位数字精度。依据：[微软说明](https://support.microsoft.com/en-us/excel/keeping-leading-zeros-and-large-numbers)。
6. 从网页实际下载EXE，核对显示版本、文件大小及SHA256。v1.2.0发布件95,035,957字节，SHA256为04373ae1dc21752636f1b68945edb2dca8cff19c8b005b2ace1070cbc0a72fe8。

通过条件：四个下载文件实际落盘，三个码文件12条完全一致，EXE校验一致。下载失败记录浏览器、按钮、时间及错误，修复后重新下载和核对，不把点击成功当作通过。

## 第2步：EXE导入与出图（印刷/车间人员）

1. 将下载EXE放到普通工作文件夹运行；开发试运行不得放在网站public目录，防止工具缓存进入静态资源。
2. 导入原始urls文件，确认识别12条。另分别用TXT、CSV独立导入，各自仍识别12条；再将同批多个文件合并导入，唯一数应仍为12。
3. 使用“导入平台文件出图”路径；本轮不使用工具中的离线应急造码，避免产生另一套码。
4. 选择QR，在独立输出目录生成12张PNG；再选择DataMatrix，在另一个目录生成12张PNG。核对输出数量、文件名对应关系和失败提示。
5. 开发使用独立识码方式回读全部24张图片，内容逐条对应原始urls；无丢码、重复代替、错码或地址变化。
6. 记录模块、静区和输出图尺寸。正式标签参数由样张实扫决定，不以默认像素值替代实际印刷验收。

通过条件：普通厂家人员能完成导入和输出，两种码制共24张全部独立回读一致。某码制失败就定位该路径；发布范围是否暂不提供它，由项目负责人明确裁定并同步产品入口，不能留下可点击但不可用的功能。

厂家已有赋码系统可用原始码文件直接制样；EXE作为平台提供的路径仍需独立验收。正式生产采用哪个系统，就再核对哪个系统的出图内容。

## 第3步：绑定及修改范围核对（厂家码管理员＋质检）

1. 进入“码库管理”，找到第1步留档的文件，使用“新建批次并绑定”，填写真实对应的测试生产批号、日期、合格证号及有效期；核对本文件12条绑定成功。
2. 已留档码不再次通过“追溯码上传”来绑定；再次上传会被视为库内已有。现成外部包装码另用上传校验与绑定流程，不重写原包装码。
3. 对一条码只修改生产日期，提交前核对影响1条；保存后该码有效期保持原值，其他码日期不变。
4. 对本上传文件只修改生产日期，提交前核对影响本文件的12条；有效期保持，另一上传文件及生产批次原值保持。当前页面的文件操作按整份文件范围执行。
5. 冻结样本尝试修正或绑定应被拒绝；恢复正常后再试。作废样本不可恢复；不合格批次应先在批次管理完成质检更正，不能在绑定表单伪造合格绕过。

通过条件：码与批次归属正确，预览数量准确，只修改明确字段，范围外数据不变。发现错绑、有效期被连带修改或部分保存，立即停止后续赋码与生产开放，保存证据交开发处理。

## 第4步：手机及微信屏幕实扫（质检）

对计划提供的码制分别操作，不预先假定微信原生扫一扫支持所有码制。

| 入口 | 操作及通过条件 |
|---|---|
| 微信自己的扫一扫 | 扫屏幕或纸张码，打开对应查询地址；核对页面和码值 |
| 手机浏览器网站扫码页 | 用户点击开启摄像头并授权，识别后进入正确查询页；当前环境不支持时应有可用引导 |
| 网站相册识码 | 从相册选择QR/DM图片，识别结果对应原始码，页面能查询 |
| 微信内网页 | 查询页可读、无白屏；扫码页按当前实现使用相册或外部浏览器引导，不将微信原生扫一扫与网页摄像头混为一项 |

每个样本都核对产品、规格、批号、生产日期、合格证号和有效期。预期结果如下：

| 样本 | 必须看到的结果 |
|---|---|
| 正常已绑定 | 展示正确产品与生产信息 |
| 未绑定 | 明确未绑定，不伪造生产信息 |
| 产品已过期 | 提示过期，展示最终有效期；单码覆盖优先 |
| 登记证已过期 | 允许按既定规则绑定，扫码提示登记证已过期 |
| 冻结 | 明确冻结提示 |
| 作废 | 明确作废，不展示产品与批次信息 |
| 有效期到期当天 | 按北京时间当天仍有效，次日过期规则由接口边界回归和日期核对共同证明 |

通过条件：实际目标入口能识别并查询，字段与预期逐项一致。未测的手机/码制/入口保留为未验。识别失败先查图片和入口；已识别但查无此码先核对环境及入库；页面字段错误交开发定位。

## 第5步：纸张和包装样张（印刷＋质检）

1. 按厂家拟采用的最小正式码尺寸及正常尺寸制样，使用实际打印机、标签材料和印刷设置；记录尺寸及参数。
2. 主样本12条先打印纸张，再制作或贴到实际包装，逐张扫码并核对结果，覆盖常见光线、取景角度和手持距离。
3. 正式选用的码制在目标入口逐张12/12通过；另一种如也对外提供，独立验收其支持范围。每张至少重复识别3次，记录失败或长时间难以识别的情况。
4. 出现失败时由印刷人员调整尺寸、清晰度、留白或位置，再整组复测；开发检查出图是否有内容差异。保留失败样张用于定位。

通过条件：实际包装上12条均能稳定识别，查询字段正确，正式印刷参数确定。小样通过前不批量印刷；测试样张和临时码不得混入正式出货。

## 第6步：记录、清理及放行（开发＋项目负责人）

逐条填写下表；失败修复后另记复测，不覆盖原失败记录。

| 编号 | 版本/环境 | 浏览器或设备/入口 | 码制/样本码 | 预期 | 实际 | 通过/失败/未验 | 证据路径 | 操作人/时间 | 复测结果 |
|---|---|---|---|---|---|---|---|---|---|
| 待执行 | | | | | | 未验 | | | |

开发汇总原始文件、全部图片回读结果、手机截图和印刷参数，按测试清单清理并核对业务基线。测试证据留在非公网目录，备份及凭据不进报告或源码包。

放行顺序：四项实操通过 → 补齐49号服务器事实和最终执行单 → 项目负责人批准具体部署 → 受控部署及线上冒烟 → 一家厂家一批真实生产试用 → 再开放其他厂家。若第0步采用正式域名停写窗口验收路径，则手机查询和包装查询在受控部署后、业务开放前完成。

试用首批按一产品、一规格、一生产批次组织码文件，采用首批实际数量。当前只完成本机1万条规模；超过1万条时先按实际数量补验耗时、内存与重试。首批检查新码数量、绑定数量、印刷使用数量和扫码结果一致；发现错码、错绑或数据损坏立即暂停该批次。
