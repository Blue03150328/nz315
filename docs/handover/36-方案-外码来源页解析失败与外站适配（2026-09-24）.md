## 2. 根因（两层，第一层是你看到的那句话，第二层伤害更大）

### 2.1 第一层 · 外站是 JS 空壳（⇒ 直接产生「未提取到产品信息」）

实抓 `http://nyzs315.com/c/z.aspx?m=c74&c=11722…`：

| 观察点 | 实测值 |
|---|---|
| HTTP 状态 / Content-Type | **200** / `text/html; charset=utf-8` |
| 体积 | **49,694 B** |
| UTF-8 解码 | **正常**（页面自带 `<meta charset=utf-8>`）⇒ **排除「GBK 乱码」这类猜测** |
| `<script>` 块 | **3 个，合计 33,181 字符 = 整页 72%** |
| 去标签去 script 后的可见文本 | 只剩 **1,567 字符 / 48 行** |
| 可见文本的形状 | `农药名称：`、`商标名称：`、`登记证持有人：`、`农药登记证：`、`剂型：`、`净含量：`、`产品批号：`、`生产日期：`、`质量保证期：`、`检验结果：`…… **冒号后面全是空的** |
| 值从哪来 | **JSONP `$.ajax`（7 处）+ `innerHTML` 回填**（12 处 XHR），运行时才写进 DOM |

⇒ `source-parser.ts` 的 `sourceText()` 第一句就是
`replace(/<(script|style)\b[^>]*>[\s\S]*?<\/\1>/gi, '')`，
把脚本整段删掉后，剩下的每个标签后面都没值 ⇒ `pairs` 为空 ⇒ `productName` / `registrationNo` / `originals` 全空
⇒ 命中 **`server/utils/source-snapshot.ts:36`** 的兜底：

```ts
if (!source.productName && !source.registrationNo && !source.originals.length)
  throw new Error('来源页面未提取到产品信息，可能需要平台适配或页面由脚本加载')
```

> 那句文案的后半截「**页面由脚本加载**」—— 作者猜得完全正确。

### 2.2 第二层 · 抛错把「本来能走通的路」一起短路了

| 位置 | 问题 | 后果 |
|---|---|---|
| `source-snapshot.ts` 的 `catch` | **`snapshot.source` 从未被赋值**（只有 try 内成功才赋） | 响应里**没有 `source` 对象** ⇒ 前端 `TraceSourceSnapshot.vue` 的 `v-if="source"` 全不渲染，**连「查看原查询页（平台名）」链接都不显示** |
| `trace.get.ts` L47 | `code = sourceSnapshot.source?.code \|\| ''` | parse 抛错 ⇒ `code` 保持传入值；若入口只带了 `source`（没带 `code`）⇒ **`formatValid=false`** ⇒ 直接落到 `not-found` + 「追溯码格式不符合 32 位阿拉伯数字规则」 |

**结果就是：一个「解析失败」，被放大成「用户什么都拿不到 —— 既没有原页链接，也没有登记资料」。**

## 4. 「能让用户看到外码原本页面的所有东西」——可以到什么程度

### 4.1 先明确否掉三条路（都别走）

| 方案 | 为什么否 |
|---|---|
| **无头浏览器**（Puppeteer/Chromium）渲染后再取 DOM | 服务器 2C4G、PM2 仅 800M、与 cynx **共用磁盘（约 75%）**；而且这条路径是**匿名可触发的**，等于把「陌生人可以让我们起一个浏览器进程」变成常态 ⇒ 内存/CPU/磁盘三重放大，运维成本（Chromium 版本、字体、沙箱）也极高。**明确不做。** |
| **iframe 内嵌原页** | 外站未设 `X-Frame-Options` 也无 CSP 时技术上可行，但：① 页面靠百度定位 SDK + 微信授权，嵌入后大概率白屏；② 用户在**我们的域名下**看到**别人的页面**，真伪判断会被混淆（防伪工具最不能有的副作用）；③ 拿不到数据就无法落库、无法比对。 |
| **抓整页 HTML 原样搬给用户看** | 同上第二条；并且我们现在的 `raw_document` 落库已经有存储放大问题（见 §6）。 |

### 4.2 能达成的最接近版本 = 三档，可分别上线

| 档 | 内容 | 拿到多少信息 | 成本 | 是否必修 |
|---|---|---|---|---|
| **档 1 · 把原页链接还给用户** | 解析失败也回填 `sourceUrl` + `platform`，前端照常显示「查看原查询页（nyzs315.com）」 | 用户**自己点过去看原页面的一切** —— 这正是你说的「引用外码扫描生成的链接」 | 极小（1 个类型字段 + 1 处赋值 + 前端 1 个 `v-if` 改判据） | ✅ **必修**（现在连这个都没有，是纯 bug） |
| **档 2 · 从 URL 里把 32 位码捞出来** | 复用**现成原语** `extractTraceCode()` ⇒ 登记库比对主链路不再被短路 | 本平台登记资料（名称/持有人/剂型/毒性/含量/成分/有效期）+ 逐项比对 | 极小（**实测该原语对这条 URL 直接返回码**，见 §5.2） | ✅ 建议必修（对所有「码藏在 URL 里」的外站都通用） |
| **档 3 · 为该平台做适配器** | 按 host 命中白名单 ⇒ 直接调它自己的 JSON 接口 | **结构化拿到外站绝大部分可见信息**（见 §5.3 字段表） | 中（新适配器文件 + 字段映射 + 比对参考来源配套） | ⚠️ 需你先认 §5.3.4 那笔账 |

> **一句话**：档 1+2 是「把我们已经有的东西还给你」，档 3 才是「把外站的东西搬过来」。**档 3 拿不到「所有东西」**——见 §5.3.3 里那三个**在源头就是空的**字段。

## 5. 方案设计

### 5.1 档 1（必修）· 解析失败也要把来源信息还给用户

**改法**（3 处，全部向后兼容）：

1. `shared/types/source-snapshot.ts`：给 `SourceSnapshot` 增两个可选字段
   ```ts
   /** 来源页网址：无论解析成败都必须回填 —— 否则用户连「自己去原页看」这条退路都没有 */
   sourceUrl?: string
   /** 来源平台（hostname），用于文案「查看原查询页（nyzs315.com）」 */
   platform?: string
   ```
2. `server/utils/source-snapshot.ts`：在 `collect()` 开头（**try 之前**）就赋值：
   ```ts
   snapshot.sourceUrl = sourceUrl
   try { snapshot.platform = new URL(sourceUrl).hostname } catch { /* 非标准 URL 就不给平台名 */ }
   ```
   ⚠️ 注意**不能**写成 `try { … } catch {}` 之外再 `new URL()` —— `source-snapshot.ts` 的既有风格是「抓取/解析失败也要能落库」，这里同理。
3. `app/components/TraceSourceSnapshot.vue`：
   - 「查看原查询页」的 `v-if="source"` 改为 `v-if="snapshot.sourceUrl"`，平台名取 `snapshot.platform || '外部页面'`；
   - `v-if="source"` 包住的两个区块（产品信息 / 生产信息 / 原药信息）**保持原样**（那本来就是「有解析结果才展示」）。

**兼容性**：旧的历史快照（`payload` 里没有这两个字段）在新版页面上就是「不显示原页链接」，与今天行为一致 ⇒ **老数据无需迁移**。

### 5.2 档 2（建议必修）· 从来源 URL 提取 32 位码

**关键发现：现成原语已经能直接取出来，不需要写任何新规则。**
实测（`node --experimental-strip-types` 直接 import 项目的 `shared/utils/trace-code.ts`）：

| 输入 | `extractTraceCode()` 返回 |
|---|---|
| `http://nyzs315.com/c/z.aspx?m=c74&c=11722252247250743408010974953971` | **`11722252247250743408010974953971`** ✅ |
| `http://nyzs315.com/I?m=c74&c=11722252247250743408010974953971` | **同上** ✅ |
| `11722252247250743408010974953971` | 同上 ✅ |
| `https://www.nz315.cn/trace?code=<码>` | 同上 ✅ |

⇒ 它的第 ② 路兜底「**任意查询参数值本身是纯数字码**」正好命中 `&c=<32位>`。

**改法**（`server/api/trace.get.ts`，1 处）：
```ts
if (!code && canFetch) {
  // 外站二维码常把码放在 URL 参数里（如 &c=<32位>）；先就地提取，别让「外页抓不到」把查码主链路也拖死。
  code = extractTraceCode(sourceUrl)
  sourceSnapshot = await collect()
  code = code || sourceSnapshot.source?.code || ''
}
```
⚠️ **顺序很重要**：`collect()` 之后再用 `source.code` 兜底（那是「页面自己声明了 识别代码」的情形），**但不能反过来** —— `collect()` 现在会抛错，抛了就什么都没了。
⚠️ 这个改动**不影响**原本就带 `code` 的入口（`/scan` 路径 `code` 非空 ⇒ 整块不执行）。

### 5.3 档 3 · nyzs315 平台适配器（可选，需先认账）

#### 5.3.1 分派方式：按 host 白名单，绝不按用户给的地址去拼 API 路径

```
server/utils/source-adapters/nyzs315.ts   ← 新增，一个平台一个文件
server/utils/source-adapters/index.ts     ← host → 适配器 的注册表（当前只 1 项）
```
- 只在该 host 命中白名单时才走 API 路径；**否则一律退回现有 HTML 解析**（保持所有既有平台行为不变）。
- 抓取**必须复用 `fetchSourceDocument`**（SSRF 加固：公网地址校验 + 固定解析地址 + 8s + 1MB + 并发 4），**不要新写 fetch**。
- ✅ **已实测：不需要给 `fetchSourceDocument` 加自定义请求头支持** —— 页面脚本里带了 `X-Tenant-ID: <m>`，但**不带这个头照样能通过租户解析**（返回的是业务校验错误 `firstFullAddress不能为空!`，而不是租户错误）⇒ 改造面比预想小。⚠️ 但**完整成功路径仍需带地址参数实测一次**（本文未验，见 §8）。

> 所以「让用户看到原页面的**所有**东西」这句话要打个折：**产品名/持有人/生产企业/查询次数这些能拿到；登记证号、含量、剂型、毒性接口里没有；企业简介、同箱信息在源头就是空的。**

#### 5.3.4 🔴 做适配必须认的三笔账（**这是要你拍板的核心**）

1. **会污染外站的查询次数。** `QueryCodeJson` 每调一次都会把对方 `queryCount` +1 —— 我为了验证调了几发，**已经把它从 1 推到了 3**。外站页面有一句「这是于【】第 N 次查询该产品，是【】生产的正品」；**我们替消费者查一次，就等于在外站留下一次查询记录**，可能让外站误判「这码被跨地区反复扫」。
   ⇒ 三条可选口径：① 每次扫码都查（最简单、最污染）；② **只在用户点「查看原查询页」时才查**（推荐：意图明确、次数最小）；③ 查了就按 (sourceUrl, code) 缓存 24 小时（减少重复，但首次仍会记一次）。
2. **多一次外部请求。** 每次扫码从「抓 1 个页面」变成「抓 1 个页面 + 1 个接口」，并发闸门（4）与限流（单 IP 20/分、全局 60/分）的余量要重算。
3. **对方接口随时可能变。** 它是 ASP.NET 老站的私有接口（连 `X-Tenant-ID` 租户头都还在用），无文档、无 SLA。⇒ 适配器**必须有降级**：接口失败 ⇒ 自动退回现有 HTML 解析 ⇒ 再失败 ⇒ 至少还有档 1 的原页链接。

#### 5.3.5 ⚠️ 档 3 的**关键配套项**（不做的话适配完了照样「全是资料不足」）

`source-snapshot.ts` 现在**只按 `source.registrationNo` 去 `pesticide_reg` 取比对参考**：

```ts
const [product] = source.registrationNo ? await query(... WHERE registration_no = ?) : []
```

而外站接口**不返回登记证号** ⇒ `source.registrationNo` 为空 ⇒ `product` 为 `undefined` ⇒

| 比对项 | 结果 |
|---|---|
| 完整登记证号 | `insufficient`（来源页未提供） |
| **码内登记类别及后六位** | **整块被跳过**（外层 `if (source.registrationNo && …)` 不成立） |
| 产品名称 / 含量 / 持有人 / 剂型 / 毒性 / 成分 | **全部 `insufficient`**（参考值取不到） |

⇒ **必须补**：当「来源页没给证号、但码是 32 位」时，用**码的前 8 位**去登记库取候选（复用 **`registry-lookup.ts` 的现成原语**，别自己 slice、别自己写类别过滤），把候选作为「登记参考」参与比对。
👉 这段才是档 3 真正的工作量所在，**不是写字段映射那么简单**。

#### 5.3.6 技术细节备忘

- `fetchSourceDocument` 的 content-type 白名单是 `/text\/|json|xhtml/i` ⇒ **`application/json` 能过** ✅；体积上限 1MB 对本接口（约 1.2KB）绰绰有余。
- `queryCode` 参数要传**整条页 URL**（`http://nyzs315.com/I?m=<m>&c=<码>`，即把 `.aspx` 换成 `/I`），不是裸码 —— 原页脚本就是这么构造的。
- 适配器产出的 `SourceDeclaration` 要**带上来源标注**（`sourceUrl` 用原始二维码 URL，不要用我们拼出来的 API URL），否则用户点「查看原查询页」会点到接口上去。

## 10. 🔴 17:0x 复测：三条结论被推翻（2026-09-24 当日实测更正）

> 本节由当日 17:0x 实测补充，**优先于上文 §5.3.1 / §5.3.2 / §5.3.3 的相关表述**。
> 触发：用户拿另一瓶药（`ddspp.cn` 平台）问同样的问题，我顺带把 nyzs315 接口的三个落地风险点重测了一遍。

### 10.1 `X-Tenant-ID` 头**必需** —— 推翻 §5.3.1 的「不需要」

| 实测（同码、同地址「广西壮族自治区,南宁市,青秀区」） | 结果 |
|---|---|
| **带** `X-Tenant-ID: c74` | ✅ `tag:1` 查询成功，1,396 B 完整数据 |
| **不带** | ❌ `tag:0` **`该码未找到相关信息!`**（1,168 B） |

⇒ §5.3.1 那句「✅ 已实测：**不需要**给 `fetchSourceDocument` 加自定义请求头支持」**作废**。
当时之所以误判：**空地址的错误先触发**（返回「firstFullAddress不能为空!」），把「缺租户头」这个问题掩盖了；地址补上后租户头才成为唯一的拦路石。

🔴 **连带硬要求**：`fetchSourceDocument` 必须新增**可选的自定义请求头**能力（向后兼容，默认行为零变化），否则适配器拿不到数据。
⚠️ **绝不要把 fetch 复制一份** —— 那会丢掉 SSRF 加固（公网地址校验 + 固定解析地址 + 8s + 1MB + 并发 4）。

### 10.2 地址必须三级，但**地区不影响返回内容** —— 补充 §5.3.2

| `firstFullAddress` | 实测结果 |
|---|---|
| `广西壮族自治区,南宁市,青秀区` | ✅ 1,396 B 完整数据 |
| `广西壮族自治区,南宁市,西乡塘区` | ✅ 1,397 B 完整数据（**换区无影响**） |
| `山东省,潍坊市,青州市` | ✅ 1,396 B 完整数据（**换省无影响**） |
| `广西壮族自治区,南宁市`（只两级） | ❌ 39 B 空返回（`tag:1, message:""`） |
| `北京市,北京市,朝阳区`（省=市同名） | ❌ 39 B 空返回（同上） |
| 完全不带地址 | ❌ `firstFullAddress不能为空!` |

三条结论：
1. **必须三段**（省,市,区），两级不行；
2. **换城市照样拿到同一份数据** ⇒ 地址只承担「过校验 + 被对方记录」，**不参与内容过滤**；
3. **直辖市「省=市」格式会返回空**，别用。

⇒ 于是「服务器端没有**区级**地址」这个卡点**不成立**：固定一个正常的三级地址即可拿到数据。
⚠️ **代价（第二笔要拍板的账）**：固定地址 ⇒ 所有经我们平台发起的查询，在对方平台都记成**同一个地区**（对方页面有「这是于【地区】第 N 次查询」），可能影响对方的地区分布 / 窜货统计。

### 10.3 返回字段边界修正 —— 补充 §5.3.3

该码 60+ 个返回键里，**真正有值的只有**：
`code1` · `bookCode`（联菊·啶虫脒）· `departmentName`（青岛正道药业有限公司）· `tenantName`（山东哈维斯生化科技有限公司）· `tenantAddress`（山东省青州市东方路北段西侧）· `queryCount` · `queryTime` · `departmentId` · `redirectionUrl`(值 0)

**恒为空**：`batchNo` · `produceTime` · `checkResult` · `bookName` · `defaultStandardName` · `companyProvince/City/County` · `tenantProvince/City/County` · `dealerName` · `dealerAddress` · `impression` · `address` · `lastOptUserAddress` · **`originalMedicineList` = `[]`**

⇒ 「把外站信息搬过来」实际只搬得到 **产品名 / 登记证持有人 / 生产企业 / 企业地址 / 查询次数 / 查询时间** 六项。
**登记证号、含量、剂型、毒性在接口里根本不存在** ⇒ 仍须本平台登记库；**批次、生产日期、检验结果、原药列表在这个码的源头就是空的**（不是我们没解析）。

### 10.4 本轮付掉的账

为验证上述三点，本轮共调用 `QueryCodeJson` **6 发**，其中 **3 发成功并计入对方计数**（A/D/F），该码 `queryCount` 由 **7 → 10**；另 3 发（B/C/E）返回空、未计数。

### 10.5 顺带否掉的一个假设：**UA 不是因素**

对 `ddspp.cn` 用无 UA / `node` / `curl/8.0.1` / iPhone Safari 四种 UA 抓取，返回**逐字节相同**的 235,414 B，解析结果完全一致 ⇒ `fetchSourceDocument` 不设 UA **不是**任何平台失败的原因。

### 10.6 ⚠️ 顺带纠正一个前提：`ddspp.cn` **根本不需要适配器**

同轮实测：`http://ddspp.cn/u/?q=21800462100136950812284409766080` 在**线上**返回 `status:"ok"`、`resultType:"external-reg"`、**18 项比对**（15 match / 2 review / 1 insufficient），`sourceSnapshot.source` 正常存在。
⇒ 它是**服务端渲染的完整静态页，通用 HTML 解析器已经能吃下**。
🔴 **结论：适配器只该给「通用解析搞不定的平台」（JS 空壳），不要按平台数量铺开做。** 判据就是一句话——**抓下来去标签后，标签后面还有没有值**。
