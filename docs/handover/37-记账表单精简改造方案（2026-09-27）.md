# 37 · 记账表单精简改造方案（少填、突出核心）

> **日期**：2026-09-27
> **状态**：✍️ **仅方案，未动一行代码** —— 待用户裁定 §6 的三条后再实施
> **前置文档**：29 号（记账功能原始方案，本改造**不改其任何口径**）· 32 号（一键记账入口）· 34/35 号（线 B，与本事无关）
> **一句话**：把「记一笔」从**10 个字段的表单**改成**1~2 个动作的确认**——
> 金额提到主位、能点的绝不打字、非核心字段折叠，且**编辑态永不折叠**。

## 0. 先点破一个认知偏差（这决定了改造的着力点）

需求原话是「太多选项需要用户去自填」。但翻代码会发现：

> **29 号 §0 已经写死**：「数量、单价、总额自动计算，**可跳过**」；
> `BillFormModal.vue:158` 的副标题也写着「**只填产品名称也能存下来**，数量单价可以以后再补」；
> 服务端 `bill-input.ts` 全程 `allowNull=true`，`totalAmount` 缺省落 `0`。

也就是说 —— **"可跳过"早就实现了，一条都没拦你**。

真正的痛点是 **视觉压迫**，不是功能缺失：

| 现象 | 证据 |
| --- | --- |
| 打开弹窗看到 10 个输入框 + 7 个单位芯片 | `BillFormModal.vue:162-281`（共 17 个可交互元素） |
| 一屏放不下，必须滚动 | 弹窗 `max-h-[85vh]` + 表单区 `overflow-y-auto`（`:154-162`）；11.3 记录里保存按钮曾被推出屏幕 |
| 「选填」二字全被淹没 | `:209/240` 的 placeholder「选填」在 10 个字段里毫无区分度 |
| 农户记得的是"花了多少钱"，表单却让他先算单价×数量 | `:198-242` 数量、单位、单价三个字段排在总额**之前**；总额在倒数第 3 位 |

⇒ **改造的着力点在信息架构（谁先谁后、谁露谁藏），不在功能删减。** 这也意味着：**零 DDL、零口径变更、零新依赖**就能达成目标。

## 1. 现状诊断（逐字段，按"输入成本 × 是否必需"排）

默认视图（新建态）实际有这些输入位：

| # | 字段 | 控件 | 输入成本 | 统计是否依赖 | 缺省行为 | 判定 |
| --- | --- | --- | --- | --- | --- | --- |
| 1 | 产品名称 | UInput（自由文本 255） | 🔴 **高**（手机打「25%多·酮可湿性粉剂」） | 列表展示必需，**服务端必填** | 扫码预填 / 手动为空 | **必露，但必须给联想** |
| 2 | 记账日期 | date 控件 | 中 | ✅ 分组/年月/趋势 | 默认今天 | **可降为一行文字** |
| 3 | 类别 | USelect 6 选 1 | 中（要判断） | ✅ **用药/用肥恒等式依赖** | 扫码预填 / 否则"未分类" | **改芯片，自动推** |
| 4 | 作物 | UInput（自由文本 50） | 🔴 高 | ✅ 覆盖作物 + 作物分布 | 空 | **折叠 + 历史芯片** |
| 5 | 数量 | number | 中 | ❌ 不参与任何统计 | 空 | **折叠** |
| 6 | 单位 | UInput + 7 芯片 | 中 | ❌ | 空 | **折叠** |
| 7 | 单价 | number | 中 | ❌ 仅列表展示 | 空 | **折叠** |
| 8 | 总额 | number（红） | 低 | ✅ **全部金额统计** | 0 | 🔴 **提到第 1 位，放大** |
| 9 | 购买渠道 | UInput（自由文本 50） | 高 | ❌ 仅展示 | 空 | **折叠 + 芯片** |
| 10 | 备注 | UTextarea | 高 | ❌ 仅展示 | 空 | **折叠** |

**归并结论**：
- **真正的核心 = 金额（总额）+ 产品名**（一个撑起全部统计，一个撑起列表可读性）
- **可推断 = 类别**（现有 `normalizeBillCategory(productName)` 已能从产品名推，扫码链路已在用）
- **可折叠 = 数量/单位/单价/渠道/备注**（5 个，占默认视图一半以上的面积）
- **纯打字项 = 产品名、作物、渠道**（3 个，全部可用「能点就别打」解决）

## 2. 改造四原则

### 原则一：主输入反转 —— **金额优先，而不是单价×数量**

农户的心智是「这瓶药花了 45 块」，不是「2 瓶 × 22.5 元」。

- 总额上移到**表单第一位**、`text-3xl` 级大字、保持 `text-error` 红色、打开即聚焦（扫码场景）。
- 数量 × 单价移入「更多」，作为**可选细分**（想记清楚的人再展开）。

> ✅ **联动内核零改动**：现有 `totalLocked`（`:46/77-85/266`）语义天生就是"金额为主"——
> 用户手填总额即上锁，数量/单价改变不再覆盖。
> **只需把"改总额"从第 8 位提到第 1 位，逻辑一行不用动。**
> 唯一调整：总额**为空**时才用 `数量×单价` 兜底（现状如此，`bill-input.ts:107-113` 已实现，前端 `recalc()` 亦然）。

### 原则二：能点的绝不打字

| 字段 | 现状 | 改造 |
| --- | --- | --- |
| 类别 | USelect 下拉（要展开、要判断） | **6 个芯片**平铺，一眼可选，不点也行（默认"其他"） |
| 产品名（手动场景） | 空输入框，全手打 | **联想下拉**：输入 1~2 字即出候选 = 本人历史产品（带上次金额）→ 本人扫过的产品 → 全平台产品库；另**直接列出最近 3 个产品做成芯片**（"上次记的"） |
| 作物 | 全手打 | 折叠区内 + **历史作物芯片**（取自本人账单 `DISTINCT crop`） |
| 渠道 | 全手打 | 折叠区内 + 芯片（农资店 / 网购 / 厂家直供 / 其他） |
| 日期 | date 控件 | **「今天 / 昨天 / 前天」三个芯片**（默认已选中"今天"，不改就零操作），需要更早再展开日历 |

> 联想数据**全部来自已有表**（`farm_bill` 本人的历史 / `scan_log` 本人的扫码史 / `product` 产品库），
> **零 DDL、零外部调用**。且**只查本人数据**（账单是私人数据，不接受跨用户推荐）。

### 原则三：两态表单（简版 / 完整版）—— 简版只在"产品名已具备"时成立

| 场景 | 默认视图 | 用户动作 |
| --- | --- | --- |
| **扫码记账**（`initial.code` 有值，产品名+类别已预填） | **金额**（1 项） | 填个数字 → 保存 |
| **手动记账**（账本页"记一笔"） | **产品名 + 金额**（2 项，产品名给"上次记的"芯片） | 点一下产品 → 填数字 → 保存 |
| **「再记一笔」**（从既有账单复制） | **金额**（产品/类别/作物/渠道/单位全部带过来） | 改个数字 → 保存 |
| **编辑既有记录** | 🔴 **永远完整展开** | —— |

> 🔴 **编辑态必须完整展开**（硬规则）：若编辑时把字段藏起来，用户会以为"我上次填的作物/单价丢了"，
> 会重复填写或误删。**折叠只对"新建"生效。**

### 原则四：复用 > 新增

- 复用 `normalizeBillCategory()`、`BILL_UNITS`、`BILL_LIMITS`（不新增口径常量文件）
- 常见作物/渠道清单与 `BILL_UNITS` **同性质**（只是"省打字"的快捷填入，**不是白名单**）—— 与 29 号 §5 裁定 #4「纯自由输入」不冲突的**前提**是：**输入框依然可以打字**，芯片只是捷径。⚠️ 但这条形式上是"加了预设"，**需用户确认**（见 §6-①）。
- **"记忆上次单位/渠道"用服务端返回，不用 localStorage** —— 29 号 §5 裁定 #2 明确否决 localStorage（怕丢数据）。
  本次是 UI 偏好而非账单暂存，性质不同，但**为免争议一律走服务端**（`/api/bill/suggest` 一并返回）。

## 3. 改造后的表单长什么样（信息架构）

```
┌─────────────────────────────────────┐   ← 头部固定
│ 记一笔                    [扫码带入] │
│ 填个金额就好，其他可选               │
├─────────────────────────────────────┤   ← 简版：不滚动，一屏装完
│                                     │
│  金额（元）                          │
│  ¥  45.00            ← 3xl 红色、聚焦 │
│                                     │
│  今天 ▾   ← 一行文字，点开才改日期    │
│                                     │
│  产品：25%多·酮可湿性粉剂 [改] ← 扫码预填，手动态才露输入框
│                                     │
│  类别   (杀虫)(杀菌)(除草)(杀螨)(肥料)(其他)
│         ↑ 已按产品名自动推好，划一下就能改
│                                     │
│  ▸ 更多（作物 / 数量·单位·单价 / 渠道 / 备注）
│                             [取消] [保存]
└─────────────────────────────────────┘
```

**默认可见 = 金额 + 日期一行 + 产品(或类别芯片) ≈ 3 个输入位**（现状 17 个），
且**唯一必打字的项是金额那 2~3 个数字**。

## 4. 「再记一笔」—— 成本最低、收益最高的一条（强烈建议同批做）

农户**复购同一款药是常态**。与其把表单改得更聪明，不如**让他根本不用填**：

- 账本列表每行（`app/pages/bill/index.vue:227-230` 现只有编辑/删除）增加一个 `i-lucide-copy-plus` 按钮
- 点击 → 打开 `BillFormModal`，`initial` = 该条 **但 `id` 置空**（= 新建而非编辑），
  **日期默认改成今天**、**金额清空**（或保留并全选，让用户直接覆盖）
- 用户动作 = **点一下 + 改个数字 + 保存**

> 实现要点：`BillFormModal` 已支持 `initial` 预填（`:88-104`）；
> **必须显式清掉 `id`**，否则会走 `PATCH` 变成改旧账（`:47` 的 `isEdit` 判定）。

### 5.3 `GET /api/bill/suggest` 形状（断言前先看，别猜）

```jsonc
// GET /api/bill/suggest            ← 一次取全，前端打开表单时懒加载（不阻塞首屏）
{
  "products": [                     // 上限 10；本人历史优先，按最近使用降序
    { "name": "25%多·酮可湿性粉剂", "category": "杀菌",
      "lastAmount": 45.00, "lastDate": "2026-08-12", "count": 3, "from": "bill" },
    { "name": "草甘膦异丙胺盐", "category": "除草",
      "lastAmount": null, "lastDate": null, "count": 0, "from": "scan" }
  ],
  "crops":    ["柑橘", "甘蔗"],      // 本人账单 DISTINCT crop，按频率降序，上限 8
  "channels": ["农资店", "网购"],     // 本人账单 DISTINCT channel，上限 6
  "unit":     "瓶"                   // 本人最近一条账单的 unit
}
```

**实现口径（3 条 SQL，逐条都有理由）**：
1. `products` 主源 = `SELECT product_name, category, MAX(bill_date), COUNT(*) FROM farm_bill WHERE consumer_id=? GROUP BY product_name`
   —— **本人历史是最高质量的候选**（他买过的就那几种），且`lastAmount` 让"复购同款"一点即填。
2. `products` 补源 = `scan_log JOIN product`（本人扫过但还没记过账的）——**扫码 = 关注/买过**，是很强的信号，且**已有现成联表写法**（`consumer/history.get.ts:13-26` 可照抄）。
3. `category` 一律过 `normalizeBillCategory()` —— 与表单预填、服务端落库**同一函数**，避免出现第 4 套口径。

**安全/性能**：
- `requireConsumer` 必填（未登录 401）；**所有查询带 `consumer_id = ?`**（本项目有 P0 水平越权前科 `1db9535`，这里绝不能省）
- 读接口，不加写限流；但注意**不要**返回全平台产品名（首发不做，见 §9）
- 单表小数据（本人几十~几百条），无性能压力；**无需索引新增**（`idx_consumer_date` 已覆盖）

## 9. 明确「不做」（YAGNI，防范围膨胀）

- ❌ **不做全平台产品名联想**（`pesticide_reg` 97,471 条 / `product` 全库）——
  公众端暴露全平台产品清单没有必要，且"别人家产品名"对本人记账毫无帮助。**首发只做本人的历史 + 扫码史**。
- ❌ **不做语音输入 / OCR 拍照记账** —— 听起来炫，但手机端实现成本远超收益，且农户场景识别率不可保证
- ❌ **不做多步向导（wizard）** —— 记账是高频重复动作，向导每步都要翻页，比单屏折叠更慢。
  **向导适合低频复杂表单，不适合记账。**
- ❌ **不做 localStorage 记住上次选择** —— 29 号裁定 #2 已否决本地暂存；本次走服务端 `suggest` 返回值
- ❌ **不改 `farm_bill` 表结构**（不加"常用产品"表、不加字段）
- ❌ **不做账单导出 / 预算预警**（29 号 §8 已明确不做，不借本次复活）
