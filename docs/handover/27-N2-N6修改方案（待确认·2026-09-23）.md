## 1. N5 —— 门户首页的伪造统计数字

### 方案

**A（推荐）：改成真数**
改 `server/api/stats.get.ts`（现在是 8 行硬编码），换成两个真实计数 + **进程内缓存 60s**：

```ts
// 首页统计卡片：真实计数（原为硬编码演示值，2026-09-23 修复）
// 为什么要缓存：首页是公众高访问路径，不能每次请求都 COUNT 全表
let cached: { at: number; data: { totalQueries: number; abnormalClues: number } } | null = null
const TTL_MS = 60 * 1000

export default defineEventHandler(async () => {
  if (cached && Date.now() - cached.at < TTL_MS) return cached.data
  try {
    const [q] = await query<any[]>('SELECT COUNT(*) AS c FROM scan_log')
    const [a] = await query<any[]>('SELECT COUNT(*) AS c FROM risk_alert')
    const data = { totalQueries: Number(q?.c || 0), abnormalClues: Number(a?.c || 0) }
    cached = { at: Date.now(), data }
    return data
  } catch {
    // 查询失败宁可回 null（前端 `stats?.totalQueries || '--'` 会显示 --），也不显示假数
    return { totalQueries: null, abnormalClues: null }
  }
})
```

**B（保守）：先撤下**
`app/pages/index.vue` 把这两张卡片改成不依赖该接口的静态文案（或直接隐藏）。零后端风险，但丢掉一个卖点。

### 影响

- 改 1 个文件（B 是 1 个文件）；**零 DDL / 零依赖 / 零 nginx / 零 `.env`**；**需要 build + reload**。
- 性能：`scan_log` / `risk_alert` 的 `COUNT(*)` 走主键聚簇索引全扫 —— 本机 `scan_log` 仅 **204 行**，线上量级也不大，**加上 60s 缓存后压力可忽略**。若将来行数到百万级，再换成计数表或 `information_schema` 估算（**本期不必**）。
- 🔴 **它已经在线上公开展示** ⇒ 修复本身没有额外风险，但**要么并入 ycdb 上线，要么单独热修一次**（成本与上线同：build + reload）。**没有"零部署"的止血办法**（数字是 SSR 时算出来的，nginx 改不了）。

### 边界

1. **口径必须写进页面注释**（否则下一个人又不知道这数字算什么）：① 「累计查询」= `scan_log` 行数 —— ⚠️ **只统计本平台签发的码**（扫到非本平台码走 `external-reg` 分支，**刻意不写 `scan_log`**，见 `trace-registry` 的只读边界）⇒ 首页数字会**低于**真实扫码总量，这是**设计使然**，别当 bug。
2. 「异常线索」= `risk_alert` 全量行数（含已处理）。若你要的是"待处理"，把 SQL 加 `WHERE handle_status = 0`（口径不同但都是真数）。
3. 接口**继续保持无鉴权**（首页是 SSR+公众页，加鉴权会白屏）；但因此**任何人都能读到这两个数字** —— 这没问题，它们是总计数，不含任何企业/用户信息。
4. 不做的事：**不引入图表、不做同比环比**（超范围）。

### 修改后的情况

| 项 | 改之前 | 改之后 |
|---|---|---|
| `GET /api/stats` | 恒 `{"totalQueries":128630,"abnormalClues":42}` | 真实计数（随业务变化），60s 内复用缓存 |
| 公网首页 | 展示编造的 128630 / 42 | 展示真实数字；**查询失败时显示 `--`**（`index.vue` 已有 `\|\| '--'` 兜底，无需改前端） |
| 验收判据（可直接粘） | — | ① `curl -s https://www.nz315.cn/api/stats` 的值**不等于 128630**；② 连打两次，第二次明显更快（缓存生效）；③ 与库内 `SELECT COUNT(*) FROM scan_log` **一致** |

**① 缓存加上限 + 淘汰**（照抄 `ip-geo.ts` 的既有写法，保持项目风格一致）

```ts

```

**② 坐标范围校验（非法即短路，0 次外部调用）**
`:50` 现在是 `if (!Number.isFinite(lng) || !Number.isFinite(lat))`，补范围：

const inRange = lng >= -180 && lng <= 180 && lat >= -90 && lat <= 90
if (!Number.isFinite(lng) || !Number.isFinite(lat) || !inRange) {

**③ 同 IP 轻量限流**

// 超限返回 429 + 中文提示，而不是丢数据（避免用户以为"附近没店"）

`nuxt.config.ts` 的 `runtimeConfig` 加 `amapPoiKey`（新 env `AMAP_POI_KEY`，**注意不带 `NUXT_` 前缀的运行期不覆盖 ⇒ 必须 rebuild**），`nearby.get.ts` 改用它，`ip-geo.ts` 继续用 `amapWebKey`。

**N6-b 搜索框生效**（顺带发现的第 8 条）
`app/pages/nearby-stores.vue:172-178` 有输入框（placeholder 「**搜索门店名称 / 地址**」）与「搜索」按钮，`:31` 把 `keyword` 传给了服务端 —— 但 `nearby.get.ts` **从头到尾没用过 `keyword`**（`:66-69` 写死关键词「农药」「农资」）⇒ **用户输入任何内容都没有效果**。
修法：服务端接收 `keyword` —— 但 🔴 **绝不能把用户输入直接当高德 `keywords` 透传**（任意关键词 + 任意坐标 = 把配额刷爆的口子开得更大，与 ④ 的初衷相反）。建议：
- 长度限制（≤20 字）+ 去空白；
- 优先**本地过滤**：拿现有的双关键词结果，用 `keyword` 过滤 `name` / `address`（**零额外配额**）；
- 只有本地过滤结果为空时，才用 `keyword` 打一次高德（**且在 ③ 的限流之内**）。

### 影响

- 改 1–2 个文件（④ 涉及 `nuxt.config.ts`）；**零 DDL / 零新依赖 / 零 nginx**；
- ④ 需要**新增 `.env` 项 + build + reload**（唯一涉及 env 的一条）；①②③ 与 N6-b 不需要。
- ④ 还需要**你去高德控制台新申请一把 Web 服务 key**（现有那把不要动，`ip-geo` 在用）。

### 边界

1. **不能给这个接口加登录门槛** —— 它是公众功能（消费者找附近门店），加了就等于砍功能。所以只能"限流 + 缓存 + 范围校验"，防的是**滥用**，不是"未授权访问"。
2. ③ 的限流会误伤**同一出口 IP 的多用户**（公司/校园 NAT、运营商 CGNAT，`ip-geo` 里已把 `100.64-127` 段识别为 CGNAT）⇒ 阈值要给得宽松（30/min 是宽松值），**宁可放过也不要让正常用户看到 429**。
3. ② 用 `located:false` 而不是 400 —— **保持既有响应契约**（前端 `stores = data.rows || []`，`located:false` 走"未定位"分支）；若改成 400，前端会进 error 态、页面显示报错，属**不必要的体验退化**。
4. ④ 是**唯一需要 `.env` 变更**的一条 ⇒ **改完必须 build**（Nitro `runtimeConfig` 构建期内嵌，这是项目铁律第 4 条）。若你不想动 env，可先只做 ①②③ + N6-b，**风险大幅下降但未解耦**（配额被打爆时 `ip-geo` 仍会静默返 null）。

### 修改后的情况

| 场景 | 改之前 | 改之后 |
|---|---|---|
| 匿名（无 cookie）调用 | 200，且能推动 2 次高德调用 | 仍然 200（公众功能，**不放登录门槛**），但受 ③ 限流约束 |
| `lng=999&lat=999` | 通过校验 → **打 2 次高德** | **短路返回**，**0 次外部调用** |

## 3. N4 —— 「登记证已过期 ⇒ 暂停绑定批次」

### 方案

**新建 `server/utils/product-guard.ts`**（一个公共守卫，三个入口共用；避免三处各写一套又漂移）：

```ts
// 绑定生产批次前的产品合规守卫（PRD 5.9 异常4：登记证已过期 ⇒ 暂停绑定批次）
export async function assertProductBindable(productId: number | null | undefined): Promise<void> {
  if (!productId) return
  const [p] = await query<any[]>(
    'SELECT registration_no, registration_expire FROM product WHERE id = ? LIMIT 1', [productId])
  if (!p) return
  const expire = String(p.registration_expire || '').slice(0, 10)
  if (!expire) return                       // 未填有效期 ⇒ 不拦（保持既有数据可操作）
  if (expire < new Date().toISOString().slice(0, 10)) {
    throw createError({
      statusCode: 400,
      statusMessage: '该产品登记证（' + (p.registration_no || '') + '）已于 ' + expire + ' 到期，不可绑定生产批次，请先更新登记证有效期',
    })
  }
}
```

**三个文件 4 处调用（插入点已按行核准）**：

| # | 文件 | 插入位置 | 传什么 |
|---|---|---|---|
| 1 | `server/api/admin/codes/batch-correct.post.ts` | **`:42`（批次查出后）与 `:45`（产品一致性校验）之间** | `batch.product_id`（`:45-50` 已保证所选码产品与之一致） |
| 2 | `server/api/admin/codes/[id]/correct.post.ts` | **`:49`（批次查出后）之后、`:51` 之前** | `code.product_id ?? batch.product_id` |
| 3 | `server/api/admin/codes/upload-batches/[id]/correct.post.ts` **①新建批次绑定** | **`:111` 之后、`:113` 的 UPDATE 之前** | `productId`（该文件作用域内已有） |
| 4 | `server/api/admin/codes/upload-batches/[id]/correct.post.ts` **②重新绑定** | **`:141` 之后、`:142` 的 UPDATE 之前** | `productId` |

> ⚠️ 只加这 4 处，**不要顺手加到 `batches/[id].patch.ts`** —— 它不是绑定入口（见本文档头部更正）。

### 影响

- **1 新文件 + 3 文件 4 处**；**零 DDL / 零依赖 / 零 nginx / 零 `.env`**；需要 build + reload。
- 每个绑定请求**多 1 次 `product` 主键查询**（`WHERE id = ?` 走主键，开销可忽略）。批量绑定场景每次请求多 1 次查询，**不是 N+1**（按批次/上传批次校验一次）。
- 上线后可能出现**"以前能绑、现在被拦"** —— 这是**预期行为**（正是本次修复的目的）。建议**先跑一段只读 SQL 看看线上有多少产品会被拦**（见下方边界 1）。

### 边界

1. **历史数据不回溯**：已绑定的码**不回收、不改变**（本次只拦"新的绑定动作"）。⇒ 上线前建议先量一下影响面：
   `SELECT COUNT(*) FROM product WHERE registration_expire IS NOT NULL AND registration_expire < CURDATE();`
2. **只拦"绑定批次"，不拦"生成码"** —— 严格按 PRD 处置层级（"暂停绑定批次"）。生成码是码池入库、不代表生产行为。
3. **不拦"编辑批次"**（`batches/[id].patch.ts`）与**不拦"字段修正"**（`produceDate/expireDate/qcResult` 类修正）—— 那些是**纠错**场景，拦了会让已过期的历史数据永远修不回来。
4. **`registration_expire` 为空的产品不拦**（保持既有数据可操作）。⇒ 代价：没填有效期的产品是个"后门"。若要堵，需要把它变成**必填**（那是产品决策，**本次不做**）。
5. ⚠️ **日期比较沿用项目既有口径 `new Date().toISOString().slice(0, 10)`（UTC 日期）**，与 `trace.get.ts:181` 一致。副作用：**东八区凌晨 00:00–08:00 之间，UTC 日期还是前一天** ⇒ 到期当天凌晨会多放行 8 小时。**本次刻意保持一致**（引入第二套口径 = 两处判断打架，更糟）；若要统一修，应**连同 `trace.get.ts` 一起**改成按北京时间（那是独立的一条，别混进本次）。
6. `products/[id].patch.ts` 把有效期**改成过去日期**时，本次**不提示、不联动**（已绑定的码不受影响）。可选增强：编辑时若检测到"新有效期已过期且该产品有已绑定码"→ 返回 warning（**非阻断**）。**待你定要不要加。**

### 修改后的情况

| 场景 | 改之前 | 改之后 |
|---|---|---|
| 绑定批次（登记证有效） | 成功 | **成功**（无感，多 1 次主键查询） |
| 绑定批次（登记证已过期） | **成功**（消费者扫码才看到红字） | **HTTP 400** + 中文提示「该产品登记证（PDxxxx）已于 YYYY-MM-DD 到期，不可绑定生产批次，请先更新登记证有效期」 |
| 单码换绑（已过期） | 成功 | 400，同上 |
| 上传批次新建/重绑（已过期） | 成功 | 400，同上 |
| 已绑定的历史码 | 不变 | **不变**（不回溯） |

**验收判据**：拿一个 `registration_expire < 今天` 的产品 → 走任一个绑定入口 → 期望 **400 + 上述文案**；对照一个有效期正常的产品 → 期望 **200**。（本机可用 `【测试】异常场景演示企业` 的数据造，**别碰线上**。）

## 4. N2 —— 公众端「信息有误，点此反馈」

### 方案（**A：真做，且复用 `risk_alert` ⇒ 零 DDL、不新建后台页面**）

> 关键洞察：PRD 要的「核实工单」，**后台的风险预警中心就是现成的工单系统**（有列表 / 详情 / 证据 / "已核实合规"、"已确认违规" 处理动作 / 导出）。
> ⇒ **不必新建表、不必新建页面**，消费者反馈直接落 `risk_alert(alert_type=7)`，复用 `triggerAlert` 的"同码同类未处理则累计"合并逻辑。

**① 新增 `POST /api/feedback`**（公众可写 ⇒ **必须防刷**）

```ts
// 公众端扫码反馈（PRD 8类异常-7「扫码页信息有误，点此反馈」入口 + 核实工单）
// 落库方式：复用 risk_alert(alert_type=7) ⇒ 零 DDL，后台在「风险预警」里处理
// 防刷：同 IP 同码 5 分钟 1 次；同 IP 每小时 5 次（进程内计数，PM2 单实例）
```

请求体与校验：
- `code`：**必须 32 位数字**（复用 `shared/utils/trace-code.ts` 的 `isTraceCode`）⇒ 非本平台码也允许反馈（消费者的现实场景）。
- `content`：**10–500 字**（少于 10 字基本是垃圾）；`contact`：选填，≤64 字，**不校验格式**（降低门槛）。
- `resultType`：入参白名单校验（防止把任意字符串写进 evidence）。

落库：用 `code` 查 `trace_code` 拿 `id / product_id / enterprise_id`（**可能全为空** —— 非本平台码时），然后

```ts
await triggerAlert(event, {
  alertType: 7,
  enterpriseId: codeRow?.enterprise_id ?? null,
  code, codeId: codeRow?.id ?? null, productId: codeRow?.product_id ?? null,
  evidence: { source: 'consumer-feedback', resultType, content, contact: contact || null,
              scanTime: new Date().toISOString(), ip: clientIpOf(event) },
})
```
`triggerAlert` 已经用 `<=>` 处理 null 键，**无需改造**。

**② 前端入口**
- `app/components/TraceAlert.vue:145`：把 `v-if="outcome.resultType === 'mismatch'"`（**永不成立**）删掉，改为**除 `voided` 外都可反馈**（作废码是终态，不必收集）。
- `app/components/TraceResult.vue`（**正常正品页**）：加一个低调的文字入口「**信息与包装标签不一致？点此反馈**」。
  > 🔴 **这一步很重要且容易漏**：消费者要发现"信息与标签不符"，**必须先在页面上看到产品信息** —— 而产品信息只在 **genuine 页**展示。
  > 只把入口放在异常页 = 把最需要反馈的人挡在外面。**请确认你同意在 genuine 页也加入口。**
- 反馈弹窗用 `UModal` + `UTextarea`（Nuxt UI v4），提交后 toast「已收到反馈，我们会尽快核实」。
- 顺带删掉 `handleFeedback` 里那句「信息反馈功能建设中，敬请期待」以及 `CONFIG.mismatch` 这条**永不可达**的配置（`:40-46`）。

### 影响

- **1 新接口 + 2 个 vue**（+ 可选 `server/utils/rate-limit.ts`，与 N6③ 共用）；**零 DDL / 零新依赖 / 零 nginx / 零 `.env`**；需要 build + reload。
- 🔴 **它是一条新的公众可写路径** ⇒ 安全上必须盯住：**限流 + 长度限制 + 不落任何敏感信息 + 不完全信任入参**（`resultType` 白名单）。

### 边界

1. **消费者提交的内容 = 线索，不是结论。** 绝不能自动把码标成"存疑/作废" —— 处理动作必须留在后台由人点（现有 `alerts/[id].patch.ts` 的"已核实合规 / 已确认违规"正好）。
2. **企业站内信会被"首次触发"唤起**（`triggerAlert` 对新预警发站内信）⇒ 可能被用来骚扰企业。缓解：同码合并（同码多人反馈只累加 `repeat_count`）+ 同 IP 限流。⚠️ **残留风险**：攻击者可以**换着码**提交（每个新码都建一条新预警 + 一条站内信）⇒ **限流是唯一防线**，若你担心，可加"同 IP 每小时 5 次"以外的"全局每小时上限"（**待你定**）。
3. **非本平台码也能反馈** ⇒ `enterprise_id` 为 null 的预警会出现在后台，但**不属于任何企业**（`enterprise_id <=> NULL`）。⇒ 需确认：平台管理员能看到它们（`requireBackendUser` 的查询是否对 `enterprise_id IS NULL` 放行 —— 要读 `alerts.get.ts` 才能确认；**若不放行，这类反馈会成为后台看不见的"黑洞"**，需要在 `alerts.get.ts` 补一条 OR 条件）。**这一点我建议在实施前先验一次。**
4. 不做的事：**不做附件上传、不做工单状态机扩展、不做短信/微信通知**（超范围，且都涉及新依赖或新 env）。
5. 若你选 **B（豁免）**：那么**必须同时删掉** `shared/types/trace.ts:11` 的 `'mismatch'` 类型 + `TraceAlert.vue` 的死按钮 + `CONFIG.mismatch`，并在 23 号/PRD 台账里记"本期豁免"。**留着不删 = 下一个人还会被它骗一遍**（我这轮就被它骗进了两次点击验证）。

### 修改后的情况

| 项 | 改之前 | 改之后 |
|---|---|---|
| 公众端反馈入口 | **不存在**（按钮门在永不出现的 `mismatch` 上，且点了也只弹"建设中"） | 异常页（除作废）+ **正品页**均有入口 |
| 提交后的去向 | 无 | 后台「风险预警中心」出现 **type 7** 记录（含码、来源、结果类型、内容、联系方式、IP、时间） |
| 企业通知 | 无 | 首次触发一条站内信（同码后续反馈只累计次数） |
| 表结构 | — | **不变**（复用 `risk_alert`） |
| 防刷 | — | 同 IP 同码 5 分钟 1 次 / 同 IP 每小时 5 次 |

**验收判据**：`curl -X POST /api/feedback` 带合法 body → 200；查库 `SELECT * FROM risk_alert WHERE alert_type=7 ORDER BY id DESC LIMIT 1` 有记录且 `evidence` 含 `source=consumer-feedback`；同一 IP 连续打 6 次 → 第 6 次 **429**。

## 5. N3 —— 每日定时巡检

### 方案对比（**推荐 B**）

| | A. HTTP 接口 + crontab curl | **B. 独立脚本 + crontab（推荐）** |
|---|---|---|
| 调用 | `curl 127.0.0.1:3100/api/internal/inspect` | `/usr/local/node22/bin/node scripts/inspect-daily.mjs --apply` |
| 鉴权 | 🔴 **麻烦**：nginx 反代后 socket 也变成 127.0.0.1 ⇒ "只允许本机"必须同时判 **socket 是回环 且 `x-real-ip` 为空/回环**（`clientIpOf` **优先信头**，单用它可被伪造 `x-real-ip: 127.0.0.1` 绕过） | **不存在鉴权问题 —— 没有任何 HTTP 入口** |
| 新 env / rebuild | 要（token）或承担鉴权风险 | **都不要**（脚本照 `scripts/db-init.mjs` 的范式直连库读 `.env`） |
| 依赖 | — | 零（只用 `mysql2`，项目已有） |
| 可测性 | 要起服务 | **本机直接 `--dry-run` 就能跑** |
| 缺点 | — | `triggerAlert` 的合并逻辑要在脚本里复刻（用 SQL 实现，不难） |

⇒ **选 B**：`scripts/inspect-daily.mjs`，**默认 `--dry-run` 只打印将要产生的预警数量与明细，加 `--apply` 才写库**。

### 巡检项（**首版 3 项，按顺序**）

| # | 项 | SQL 要点 | 落预警 |
|---|---|---|---|
| ① | 登记证号不存在 | `product p LEFT JOIN pesticide_reg r ON r.registration_no = p.registration_no WHERE r.registration_no IS NULL` | **type 3** |
| ② | 登记证已过期 | `WHERE p.registration_expire IS NOT NULL AND p.registration_expire < CURDATE()` | **type 4** |
| ③ | 生产厂家不符 | `p.holder_name` vs `pesticide_reg.company`，**归一化后比较**（复用 `normalizeOrgName` 的规则，脚本里内联同款实现） | **type 6** |
| ~~④~~ | ~~产品名称不符~~ | — | **首版不做**（P1-5 已证口径会误报；等口径定了再加） |

写库复刻 `triggerAlert` 的合并语义：**同 `enterprise_id + product_id + alert_type` 且 `handle_status = 0` ⇒ `repeat_count + 1`；否则新建**。

### 影响

- **1 个新脚本**；**零 DDL / 零依赖 / 零 nginx / 零 `.env` / 不需要 build**。
- 服务器上需要：① 脚本随上线包落到 `/www/wwwroot/nz315/scripts/`；② 宝塔「计划任务」加一条 **每天 03:00** 执行：
  ```
  /usr/local/node22/bin/node /www/wwwroot/nz315/scripts/inspect-daily.mjs --apply >> /www/wwwlogs/nz315-inspect.log 2>&1
  ```
  ⚠️ **必须用 `/usr/local/node22/bin/node` 绝对路径**（系统 `node` 是 v20，是 cynx 用的那套；与 PM2 per-app interpreter 保持同一个解释器最稳）。
- 本机验收：`node scripts/inspect-daily.mjs`（dry-run）应打印三类问题的**条数与样例**，**第 2 次执行不产生新预警**（幂等）。

### 边界

1. 🔴 **本脚本是"给生产跑"的，所以安全闸的取向与 `seed-abnormal-demo.mjs` 相反**：那类造数据脚本要 `DB_HOST` 白名单；**巡检脚本绝不能设这个白名单**（服务器 `DB_HOST` 正是 `127.0.0.1`，设了就等于永远跑不起来）。它的防护是**"默认 dry-run、必须显式 `--apply`"** —— 请务必保留这个默认值。
2. 🔴 **预警表增长**：`triggerAlert` 的语义是"已处理的就新建一条"，如果每天巡检，**同一个老问题会天天新建** ⇒ `risk_alert` 会随天数线性膨胀。**必须在巡检侧加冷却**：同一个 `product_id + alert_type` **最近 30 天内已有记录（无论处理状态）就跳过**。（**冷却天数待你定**，我建议 30 天。）
3. **首跑会一次性产生一批历史预警**（线上有多少过期登记证的公司产品，跑 dry-run 就知道）。⇒ **务必先 dry-run 看数量**，若量很大（比如上百条），先决定是"全量落库"还是"只记日志不上预警"。
4. 巡检**只读业务表 + 只写 `risk_alert`**，不碰 `product` / `trace_code`。**绝不自动改数据、绝不自动作废**。
5. 巡检用的是 `pesticide_reg` 的**快照**（登记资料库是导入的静态表，不会自己更新）⇒ 巡检发现"证号不存在"可能意味着**登记库该更新了**，不一定是企业造假。**文案里要带上这个可能**（与现有 `not-found` 分支的"4 条可能原因"一个思路）。
6. 若 N1 也做了（建档阻断），那 ① 只会命中**历史数据 + 编辑路径**产生的存量 —— 这反而是它的价值（存量清理）。

### 修改后的情况

| 项 | 改之前 | 改之后 |
|---|---|---|
| 「每日定时巡检」 | **不存在** | 每天 03:00 自动跑，日志落 `/www/wwwlogs/nz315-inspect.log` |
| type 3 / 6 的触发路径 | **完全没有**（`triggerAlert` 全项目仅 3 处调用点） | 由巡检触发 |
| type 4 | 只在**有人扫码时**才触发 | 巡检兜底（**没人扫也能发现**，这才是 PRD 的本意） |
| 后台风险预警 | 类型 3、6 永远是空的 | 出现真实条目，可在预警中心走"已核实合规 / 已确认违规" |
| 手工执行 | — | `node scripts/inspect-daily.mjs` 随时 dry-run 体检 |
